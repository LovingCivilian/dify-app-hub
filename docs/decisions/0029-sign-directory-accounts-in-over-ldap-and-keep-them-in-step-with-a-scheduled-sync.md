# Sign directory accounts in over LDAP and keep them in step with a scheduled sync

## Context and Problem Statement

The backend rework charter's B3 row (`docs/superpowers/specs/2026-10-07-backend-rework-charter.md` §5) asks for LDAP sign-in, groups and per-app access, "Specified then". The B3 design spec (`docs/superpowers/specs/2026-10-09-backend-b3-groups-access-ldap-design.md`) is that specification and splits the work in two: B3a (groups, per-app access, account status; [ADR-0027](0027-gate-apps-by-groups-and-grants-and-deactivate-accounts-with-two-markers.md), merged as PR #31) and B3b (this record: directory sign-in and sync). The spec calls this record ADR-0028; the sidebar took that number ([ADR-0028](0028-navigate-the-admin-area-in-a-sidebar-shared-with-the-chat.md)), so it is ADR-0029 (ADR-0027's B3b notes say the same).

B3a built the audience and the off switch and wrote neither: hub groups whose memberships record a source (`manual` or `directory`), and `users.directory_deactivated_at`, the directory's own deactivation marker. Until B3b every account is a local one, with an email and a bcrypt hash. The company runs Active Directory, reached today by IP and port without TLS; people should sign in with their Windows username, the hub should learn who has left, and the groups people already belong to in the directory should decide which Dify apps they see.

The owner decided on 2026-10-09 (spec §2, not re-opened) the points that bind this record: #4 Active Directory first, any LDAPv3 server through settings with AD defaults, "disabled" being whatever the user filter excludes; #5 directory users sign in with `sAMAccountName`, local accounts keep their email; #6 the login page switches between "Directory account" and "Local account"; #7 roles are set in the hub only, a new directory account starts as `user`; #10 a directory sign-in whose email belongs to a local account is refused; #11 an entry without an email is refused; #12 the lifecycle (re-checked on a schedule and at each directory sign-in, two independent markers, an unreachable directory changes nothing); #13 the settings are an all-or-nothing `LDAP_*` block in `lib/env.ts`, group links are data; #14 a croner job from `instrumentation.ts` `register()` with a cron expression and an optional IANA time zone; #16 generic sign-in messages, only "the directory is unreachable" specific; #17 sign-in throttling deferred; #18 `LDAP_ENCRYPTION` is `ldaps`, `starttls` or `none`, chosen explicitly.

The question: how do directory accounts sign in, how are they linked to their directory entry and kept in step with it, and how is all of that tested without the owner's directory?

## Decision Drivers

- No account takeover, and linking by the entry's key only ([ADR-0026](0026-use-the-accounts-permanent-id-as-the-dify-end-user.md): `users.id` is the Dify end user and must survive renames and moves; next-auth's FAQ on automatic account linking warns against linking by email).
- An unreachable or misconfigured directory changes nothing (GitLab's documentation warns: "All users are blocked if the LDAP server is unavailable when an LDAP user synchronization is run", `gitlabhq@0739b8bf:doc/administration/auth/ldap/ldap_synchronization.md:196-200`).
- One generic answer for every account-related refusal (OWASP Authentication Cheat Sheet, "Authentication Responses"), including the time it takes.
- Passwords never in clear without the owner's explicit choice (RFC 4513 §5.1.3: "The name/password authentication mechanism of the simple Bind method is not suitable for authentication in environments without confidentiality protection").
- Documented approaches only, with reference projects where the docs are silent ([ADR-0002](0002-use-documented-library-approaches-only.md); run rule R0).
- Only features both MySQL and PostgreSQL have (ADR-0004 note of 2026-10-09).
- The directory owns only its own facts: it must never undo an admin's decision ([ADR-0027](0027-gate-apps-by-groups-and-grants-and-deactivate-accounts-with-two-markers.md)).

## Considered Options

The research behind the options is in `docs/superpowers/research/2026-10-09-backend-b3/` (`ldap-client.md`, `periodic-jobs.md`, `ldap-reference-projects.md`, `e2e-ldap-server.md`) and in its `b3b-plan/` folder (`library-apis.md`, `ldap-test-servers.md`, `ad-and-reference-projects.md`); the run's audit of every ruling against reference projects is `.superpowers/sdd/2026-10-10-backend-b3b-directory/refs-audit.md` (with `refs-q-u.md` and `refs-z-ah-order.md`), summarised below.

The client:

- `ldapts` 9.2.0. Chosen. Pure TypeScript, so the Alpine image needs no native build; n8n (`packages/cli/package.json:244` at `n8n@5b78e8b6`) and Backstage (`plugins/catalog-backend-module-ldap/package.json:48` at `backstage@75128025`) use it.
- `ldapjs`. Decommissioned on 2024-05-14 (npm marks it deprecated; the repository is archived).
- `@infisical/ldapjs`. A vendor's republish of ldapjs with issues disabled, not a maintained line.
- `ldap-native`. A native addon on `libldap`, one author, new.
- `passport-ldapauth`. Built on ldapjs, and a Passport strategy where this app uses next-auth.
- `ldap-authentication`. A wrapper of ldapts that adds a second maintainer and licence for about 40 lines of flow the hub has to own anyway.

The schedule:

- croner started from `instrumentation.ts` `register()`, each run claiming a unique slot in the database. Chosen. Formbricks, Homarr, Rallly and ZTNet start recurring work from the application process.
- An external cron calling a secret route (Cal.com).
- A worker container from the same image (Twenty, Langfuse).
- A job queue, which needs Redis.
- The timer library: croner 10.0.1 (chosen; Homarr pins it exactly) / `node-cron` / `cron`.

The link between a hub account and a directory entry:

- The entry's `objectGUID` or `entryUUID`. Chosen (Keycloak, Mattermost, Nextcloud and Rocket.Chat key their directory users by such a unique id).
- The DN (GitLab, Grafana, with an email fallback).
- The email (Open WebUI).
- The login name (LibreChat).

The sign-in:

- A second Credentials provider `ldap` beside the local one, and one form per tab. Chosen (next-auth, "Multiple providers"; GitLab's and Open WebUI's LDAP tabs).
- One form that tries both (Grafana, Rocket.Chat).

An unknown username's timing:

- A response-time floor. Chosen (Authelia).
- A dummy bind. No surveyed project does it, and a domain controller forwards a wrong password to the PDC emulator, so the timing would still differ.
- Nothing (Spring Security, django-auth-ldap, n8n).

The test directories:

- Samba's `smblds` over LDAPS and OpenLDAP 2.6 over StartTLS and plain. Chosen (os2mo and authentik run a Samba DC beside OpenLDAP).
- OpenLDAP only (Mattermost, GitLab QA, ldapts).
- `smblds` only.

The test certificates:

- Committed, with a regeneration script. Chosen (python-ldap, Node.js core, Go).
- Generated at test time (ldapts with node-forge, authentik).
- Generated in a container at start.

The groups page's directory search:

- A GET Route Handler `app/api/directory/groups`. Chosen (react.dev `'use server'` Caveats; Next 16.3.4's `server-actions.md`, `07-mutating-data.md` and `backend-for-frontend.md`: Server Functions are for mutations, queued, "not recommended for data fetching"; decision al).
- A Server Action (the spec's §6.5 text; deviation 10).

## Decision Outcome

Chosen: `ldapts` 9.2.0 and `croner` 10.0.1; accounts linked by the entry's key (`users.directory_id`) and created at first directory sign-in as `user`; a second Credentials provider `ldap` with its own tab on the login page; a sync started from `instrumentation.ts` with a slot claim, safety stops and idempotent writes of only what the directory owns; hub groups linked to directory groups on the groups page, searched through a GET Route Handler; status and Sync now on the users page; `LDAP_ENCRYPTION` including `none`, with the trade-off written down; and the two test directories behind a Vitest project of their own, because each keeps one writer per fact, never trusts a directory answer it cannot verify, and tells a person nothing a stranger could use.

The sections below record what was built, in the order of the plan's tasks. The plan's decisions are lettered a to aq and its deviations numbered 1 to 11 (the plan lists 1 to 10; the review of Task 1 added 11); each carries its documented source and, where the docs are silent, two or three pinned reference projects (rule R0). Where the run's rulings changed the plan's text, this record states what was built.

### The data model, as built (Task 1)

- `db/schema/users.ts`: `source` (`mysqlEnum('local','ldap')`, default `local`, `NOT NULL`), `directory_id` (`varchar(64)`, unique index `users_directory_id_key`), `directory_id_attribute` (`varchar(64)`, the attribute that produced the key) and `directory_username` (`varchar(255)`); `password` becomes nullable. The key is a lowercase 8-4-4-4-12 UUID string (RFC 9562 §4): for `objectGUID` in Microsoft's byte order, for `entryUUID` lowercased.
- The `users_source_credentials` CHECK (MySQL 8.4 "CHECK Constraints"): `(source = 'local' AND password IS NOT NULL AND directory_id IS NULL) OR (source = 'ldap' AND password IS NULL AND directory_id IS NOT NULL AND directory_id_attribute IS NOT NULL)`. A directory account has no hub password, and the database refuses a write that would give it one (error 3819).
- `db/schema/directory.ts`: `user_group_directory_links` (`group_id` with a cascading foreign key to `user_groups`, `directory_group_id` the group's key, `directory_group_name` the name the groups page shows, `missing_since`; primary key `(group_id, directory_group_id)`) and `directory_sync_runs` (UUID `id`, unique `slot`, `run_trigger` (`schedule`, `startup`, `manual`), `started_at`, `finished_at`, `outcome` (`running`, `succeeded`, `failed`, `empty`, `id_attribute_changed`), the counts `entries_seen`, `deactivated`, `reactivated`, `updated`, `conflicts`, `group_errors`, `memberships_added`, `memberships_removed`, and a fixed `error_code`; an index on `started_at`).
- One generated migration, `db/migrations/20261010071751_b3b-directory/`. Every existing account becomes `local`. The CHECK must hold on the existing rows, so a database whose `users.password` holds a NULL cannot be migrated until that row is fixed.
- Deviation 11 (Task 1's review, taken as a ruling): the CHECK's `ldap` branch also requires `directory_id_attribute IS NOT NULL`, stricter than spec §3.2's text. Spec §3.2 calls the column "the attribute that produced the key", so every key has one, and the `id_attribute_changed` stop of spec §6.4 step 2 reads it. Regenerating the one unmerged migration cost less than a drop-and-re-add after the owner's database had run it. The sentence for the record: the CHECK requires the attribute on every `ldap` row, so a directory key is never stored without what produced it; Supabase Auth stores an identity's id only with a non-null provider (`migrations/20210909172000_create_identities_table.up.sql:3-13` at `supabase/auth@ce9a8eee`), authentik's directory link has a non-null source and identifier (`authentik/core/models.py:1125-1143` at `authentik@a40205dc`), and GitLab states the same discriminated rule as a CHECK (`check_vs_code_settings_settings_context_hash_nullable`, `db/structure.sql:34283` at `gitlabhq@0739b8bf`).
- The two migrations of B3a are untouched; the run table's trigger column is `run_trigger` because `TRIGGER` is reserved in MySQL 8.4 (deviation 2).

### Settings and dependencies (Task 2)

- `lib/env.ts` parses an all-or-nothing `LDAP_*` block like the SMTP block (spec §7.1): setting `LDAP_URL` requires `LDAP_ENCRYPTION`, `LDAP_BIND_DN`, `LDAP_BIND_PASSWORD` and `LDAP_USER_BASE_DN`; the rest default to Active Directory's values (`docs/ldap.md`). The pair `ldaps://` with `ldaps`, `ldap://` with `starttls` or `none` is checked.
- `LDAP_ENCRYPTION` is trimmed and lower-cased before the enum (Task 2 review M3). The trim follows n8n (which trims every value) and the lower-casing follows Homarr's `AUTH_PROVIDERS` and the repo's own `flag()` for the SMTP flags; strict enums are also common (Homarr's LDAP scope is case-sensitive). The audit found practice mixed and the leniency harmless.
- **a. Exact pins.** `ldapts@9.2.0` and `croner@10.0.1` are installed with `pnpm add -E` (pnpm docs, `pnpm add --save-exact`), as this line pins `drizzle-orm`: ldapts is the security-relevant client (spec §6.1), and both versions are the ones the research read (`docs/superpowers/research/2026-10-09-backend-b3/b3b-plan/library-apis.md` §1, §2: 9.2.0 and 10.0.1 are `latest` on 2026-10-10; Homarr pins `croner` 10.0.1 exactly).
- **b. Configured filters are read by ldapts' own parser.** `FilterParser.parseString` is exported from ldapts' root (`src/index.ts:12`, typed in `dist/index.d.mts`) and is the parser `search()` applies to a string filter (`src/Client.ts:640-646` at `ldapts@b38cfc3`); it is pinned by ldapts' tests (`tests/FilterParser.test.ts:19-55`) but not described in the README. A filter must also start with `(` and end with `)`, as RFC 4515 §3 writes one (`filter = LPAREN filtercomp RPAREN`; ldapts' README: "ldapts requires all filters to be surrounded by '()' blocks"). `LDAP_GROUP_MEMBER_FILTER` must contain `{group_dn}` and parses with a sample DN in its place. ldapts' parser closes one missing final parenthesis of an `&`, `|` or `!` filter (`(&(objectClass=user)` is read and sent as `(&(objectClass=user))`, probed on 9.2.0; `dist/index.mjs:2246-2253`); an extra `)` or an unclosed comparison is refused, so the test's malformed filter is `(&(objectClass=user)))`. An admin's filter missing its last `)` is sent closed: what they wrote, less one character.
- **c. The schedule is a five-field cron expression or `off`.** croner's default `auto` mode also takes six and seven fields with seconds first (croner README "Pattern"), which would allow a sync every second; croner's own `mode: '5-part'` refuses any other field count (croner 10 `dist/croner.d.ts:244-255`; Task 2 review M1, so the hand count was dropped, and croner's documented nicknames such as `@hourly` pass), and the time zone is checked on its own field (below), because croner checks a zone only when it converts a date (`CronDate.fromDate` throws "Failed to convert date to timezone", `src/date.ts:277` at `croner@adc86215`). The `Cron` used to validate has no function and no `name`, so it starts no timer and joins no `scheduledJobs` list (`src/croner.ts:208, 215-219`). A pattern no date matches (`0 0 31 2 *`) parses but never fires: croner's `nextRun()` answers null (`dist/croner.d.ts:548`, `nextRun(): Date | null`), and the environment refuses it by name (spec §7.1: a bad value is named; Review Focus 4).
- A schedule croner parses but that never fires (`0 0 30 2 *`) is refused at start-up, as LibreChat does ("croner accepts syntactically valid patterns that can never match … those would arm a schedule that never fires", `packages/data-provider/src/cadence.ts:68-91` at `LibreChat@e1dfc104`) and Sim does ("Cron expression produces no future occurrences", `apps/sim/lib/workflows/schedules/utils.ts:30-41` at `sim@b1b084dd`); GitLab and Kubernetes check the syntax only.
- `LDAP_SYNC_TIMEZONE` takes an IANA time zone name only (Task 11's ruling, revising Task 2's "name or offset"): `lib/env.ts` checks it on its own field with `new Intl.DateTimeFormat(undefined, { timeZone })` (MDN: a `RangeError` for an invalid value), refuses a value whose canonical form (`resolvedOptions().timeZone`) is an offset identifier, and stores the canonical name. The sentence for the record: spec §2 #14 and §7.1 say "IANA name", and croner's README gives `timezone` as an IANA name (fixed offsets go through `utcOffset`), as GitLab's cron parser accepts TZInfo identifiers only (`lib/gitlab/ci/cron_parser.rb:79-95` at `gitlabhq@0739b8bf`), Kubernetes refuses a CronJob `timeZone` that is not "an explicit time zone as defined in https://www.iana.org/time-zones" (`pkg/apis/batch/validation/validation.go:966-990` at `kubernetes@b27a4f0d`), and n8n's `GENERIC_TIMEZONE` is an IANA name (`generic.config.ts:10-12` at `n8n@5b78e8b6`). A bad zone is refused by name even when the schedule is `off`. A zone written as an offset costs the owner a city zone or an `Etc/GMT-1` style name.
- **d. `LDAP_URL` needs a host** (zod 4 "URLs": `z.url({ protocol, hostname })`; without a hostname rule `ldap:host` passes with an empty host, which ldapts would read as `localhost`, `src/Client.ts:231`). Attribute settings follow RFC 4512 §1.4 (`descr = keystring`, a letter then letters, digits and hyphens; not a numeric OID, which RFC 4512 allows but ldapts' filter parser cannot read: it takes an attribute as `[\w-]+`, `src/FilterParser.ts:226-233`, so `(2.5.4.3=x)` fails at the search, probed), because the code writes them into filters unescaped (ldapts README "Filter Strings"; `ldap-client.md` §3.8). Non-secret values are trimmed; `LDAP_BIND_PASSWORD` is taken as it is (spaces can be part of a password). The two readers of `.env` differ on `$`. Next expands `$NAME` in `.env*` files ("If you need to use variable with a `$` in the actual value, it needs to be escaped e.g. `\$`", `node_modules/next/dist/docs/01-app/02-guides/environment-variables.md:152`), and Docker Compose, which reads `.env` through `env_file` in the container stack, takes a single-quoted value literally (Docker docs, ".env file syntax": "Single-quoted (`'`) values are used literally"). `.env.template` and `docs/ldap.md` therefore say: in `.env` a value with a `$` is single-quoted, and for `pnpm dev` it is written `\$` in `.env.development.local`, which only Next reads and which overrides `.env` (Next's load order; Task 2 review I1: the plan's plain `\$` note broke a `$` password on the Docker stack).

### The directory Data Access Layer (Tasks 3 and 9)

`lib/data/directory.ts` is the second actor-less DAL module after `lib/data/setup.ts` ([ADR-0024](0024-keep-the-apps-own-data-behind-a-data-access-layer-with-server-actions-and-gate-the-admin-surface-by-role.md)): its guard is its input (values from a successful bind or a complete directory search), and it writes only what the directory owns: `directory_deactivated_at` (with a `sessionVersion` bump), the directory fields of `ldap` accounts, `directory` memberships, the links' names and `missing_since`, and the run rows. It writes no admin marker, role, password or `manual` membership.

- **e. A retry on 1062, and up to three attempts on 1213.** Two first sign-ins of the same person at once both find no row; the locking read takes a gap lock in the unique index, so one insert waits or is rolled back as a deadlock victim (1213), or the unique index refuses the second (1062). The whole transaction runs again and then finds the account the other wrote, or the email taken: once after a 1062, and after a deadlock within three attempts in all, the sync statements' bound (final review M1; the bound's bullet below). MySQL 8.4 "How to Minimize and Handle Deadlocks": "Always be prepared to re-issue a transaction if it fails due to deadlock." B2's `createOwner` relies on the same locking read (ADR-0024 decision d). Built at `READ COMMITTED` (Task 3 review I1; `isolationLevel: 'read committed'`, Drizzle "Configure MySQL transaction options"): the gap lock above exists under REPEATABLE READ only, and different-key first sign-ins in one gap deadlock each other there. MySQL 8.4's deadlock guidance suggests READ COMMITTED for locking reads, and the repo's `createOwner` sets its own level the same way (ADR-0024 decision d). The level needs row-based binary logging ("Only row-based binary logging is supported with the READ COMMITTED isolation level"; `binlog_format=ROW` is MySQL 8.4's default, and the e2e MySQL reports ROW; a server forced to `STATEMENT` fails the write: "It is _possible_ to change the logging format to `STATEMENT`, but doing so at runtime leads very rapidly to errors because `InnoDB` can no longer perform inserts", MySQL 8.4 "Setting The Binary Log Format", the refusal being error 1665 `ER_BINLOG_STMT_MODE_AND_ROW_ENGINE`, "impossible to write to binary log since BINLOG_FORMAT = STATEMENT and at least one table uses a storage engine limited to row-based logging", MySQL 8.4 Error Reference). The live probe of the fix round measured it on the e2e MySQL: forced REPEATABLE READ rejected up to 18 of 40 and 44 of 80 first sign-ins with 1213, READ COMMITTED succeeded for all (one key 60 calls a run, different keys 60, memberships 120, three runs). `INFORMATION_SCHEMA.INNODB_TRX.trx_isolation_level` lagged in the probe and is not evidence of the level; the snapshot behaviour is, and the unit test asserts the transaction config. Correctness rests on the unique key and the retry at either level. The sentence for the record: the sign-in transaction runs at READ COMMITTED, the level Drupal recommends on MySQL and warns about when it finds REPEATABLE READ (`core/modules/mysql/src/RequirementsTrait.php:40-56` at `drupal@1e10d0d2`), and the one Nextcloud runs on and documents together with `binlog_format` (`admin_manual/configuration_database/linux_database_configuration.rst:28-58` at `nextcloud/documentation@9caf44b7`). A group deleted mid-sign-in answers 1452 on the membership insert and is not retried (Task 3 review M1, deferred: rare and self-healing, no account harm; a follow-up, final review M8).
- **f. The memberships a sign-in writes are exactly the groups it found** (spec §6.3 step 7): the person's `directory` rows in any other group, including a group whose last link was removed, are deleted; `manual` rows are never read or written (spec §2 #8).
- **g. A refresh overwrites the name with the entry's** (null when the entry has none), as LibreChat overwrites "provider, `ldapId`, email, username and name … on every login" (`LibreChat@e1dfc104:packages/api/src/auth/ldap.ts:31-35,85-89`) and Mattermost treats AD/LDAP attributes as authoritative (`mattermost/docs@bd09d959:source/administration-guide/onboard/ad-ldap.rst:111`); the email is overwritten only when no other account uses it (spec §2 #11), and an entry without an email keeps the old one (`users.email` stays `NOT NULL`).
- **ac. The unique index arbitrates an email conflict.** The plan only says "this email changed"; the write tries it and, when the unique index refuses (1062), writes the other fields and counts a conflict. The index compares as MySQL's collation does, which code cannot imitate (B3a: `utf8mb4_0900_ai_ci` is case- and accent-insensitive).
- **ae. Writes in batches of 1,000 ids**, each its own statement. The bound that applies is `max_allowed_packet` (64 MB by default; MySQL 8.4 "Packet Too Large"), because Drizzle rc.3's mysql2 session sends every query through mysql2's `query`, which fills the values in on the client, not as a prepared statement (`mysql2/session.js:28`); the 65,535 placeholders of a prepared statement (MySQL 8.4 Error Reference, `ER_PS_MANY_PARAM` 1390) are only the margin. 1,000 follows Keycloak's sync batch (`DEFAULT_BATCH_SIZE_FOR_SYNC = 1000`, `keycloak@c7de391a:server-spi-private/src/main/java/org/keycloak/models/LDAPConstants.java:87-88`), Rails (`find_in_batches(… batch_size: 1000 …)` and `in_batches(of: 1000, …)`, `rails@48dc419a:activerecord/lib/active_record/relation/batches.rb:161,259`) and Cal.com (`take: 1000`, `q2-cron-projects.md:58` in the B3 research); the reconciliation is idempotent (spec §6.4 "Claim"), so a run cut short is completed by the next.
- Every sync write re-issues on a deadlock, up to three attempts in all, and `recordDirectorySignIn` runs its transaction again after a deadlock within the same three attempts and once after a 1062 (`DEADLOCK_ATTEMPTS` in `lib/data/directory.ts`; final review M1, built in Task 16's fix wave). The audit found practice contradicts the earlier "re-issue once": Prisma's documented `withRetry` allows 3 attempts (`prisma/docs@c05758d0:apps/docs/content/docs/orm/fundamentals/transactions.mdx#L90-L104`), Ghost 3 (`TryGhost/Ghost@25b7dfad:ghost/core/server/services/app-installations/service.ts#L374`), Directus 4 with exponential backoff (`directus@8e140f94:api/src/utils/transaction.ts#L29-L50`), Vendure 6 (`vendure@e5146b14:packages/core/src/connection/transaction-wrapper.ts`) and Laravel's example 5 (`laravel/docs@d9b95fe9:database.md`). The controller re-ruled 3 attempts for both paths, the 1062 path keeping its one retry, which the unique key settles. The statement runs again at once, as in Prisma's helper and Ghost, since MySQL's guidance names no delay ("Deadlocks are not dangerous. Just try again."); the third deadlock propagates: the run fails and the next completes the idempotent reconciliation, and a sign-in answers `Default`. The cost is two extra statements in a rare deadlock.
- A sync write that cannot match a row counts `updated` only when a row was matched (`affectedRows`; mysql2's `FOUND_ROWS` default); `refreshDirectoryAccount` returns `{ updated, conflict }`; every sync write moves `users.updated_at` (Drizzle `$onUpdate`); `group_errors` counts distinct linked groups whose memberships could not be applied. The sentence for the record: `group_errors` counts linked groups, as Keycloak's group mapper counts one failure per group, each in its own transaction (`GroupLDAPStorageMapper.java:198-234` at `keycloak@c7de391a`), and authentik applies memberships group by group (`authentik/sources/ldap/sync/membership.py:92-136` at `authentik@a40205dc`).
- `latestSyncRun`, `lastSucceededSyncRun` and `listDirectoryMemberships` have pinned SQL shapes in the tests. `lib/data/directory.ts` holds two concerns, the account and membership writes and the run ledger; a `directory-runs.ts` split is a follow-up (Task 9 review M6, final review M7).

### The pure helpers and the connection (Tasks 5 and 6)

`lib/directory/{keys,filters,entry,config,errors,connection,operations}.ts`.

- **m. A key is binary when the id attribute is `objectGUID`**, compared without case, as Keycloak decides (`keycloak/keycloak@c7de391a:federation/ldap/src/main/java/org/keycloak/storage/ldap/LDAPConfig.java:182-183`, `isObjectGUID()` is `getUuidLDAPAttributeName().equalsIgnoreCase(LDAPConstants.OBJECT_GUID)`; its `LDAPUtil.java:112, 170, 229` encode, decode and filter the 16 bytes) and as Backstage formats an AD vendor's GUID (`backstage@75128025:plugins/catalog-backend-module-ldap/src/ldap/vendors.ts:126-145`). Spec §6.3 step 6 reads binary-ness from the value's length; this reads it from the setting, so the sync can rebuild a key's 16 bytes for a lookup (spec §6.4 step 4) without guessing. For the two supported attributes the result is the same: `objectGUID` is 16 bytes (Microsoft Learn `a-objectguid`: "Size: 16 bytes"), `entryUUID` is text (RFC 4530 §2.1). Spec §2 #4 already names the `objectGUID` byte order as the one vendor difference in code. The binary key reaches the directory in a filter object, not a string (deviation 9): ldapts 9.2.0's `search()` parses a string filter, reads each `\XX` escape as one character (`src/FilterParser.ts:351`, `_unescapeHexValues`) and writes the value as UTF-8 (`src/ber/BerWriter.ts:77-87`, `writeString`), so every byte from 0x80 up goes out as two and the GUID matches nothing (probed: 16 bytes sent as 27); ldapts' answer to "Filtering by objectGUID" (issue #104, closed in v3.1.0: "I added `Buffer` as a possible value type for EqualityFilter") is an `EqualityFilter` with a `Buffer` value, which `writeFilter` sends as the OCTET STRING it is (RFC 4511 §4.1.6). Spec §6.3 step 3 names "ldapts `escapeFilter` or filter classes"; the filter's string form (`toString()`) is still the per-byte escape of spec §7.2, and text keys (`entryUUID`) and every escaped character (`\2a \28 \29 \5c \00`, all below 0x80) go out byte for byte either way.
- **n. `objectGUID` is always asked for as a Buffer under its schema spelling too.** ldapts matches `explicitBufferAttributes` against the attribute type as the server sends it, case-sensitively (`src/messages/SearchEntry.ts:53`), and AD sends `objectGUID`; a setting written `objectguid` would otherwise get a string whenever the bytes happen to be valid UTF-8 (`src/Attribute.ts:57-75`).
- **o. An entry's values are read without regard to the attribute's case** (RFC 4512 §2.5: "attribute type names are case insensitive"; ldapts keys a result by the type as the server sent it, `ldap-client.md` §3.5), the first value of a multi-valued attribute is used, an email that `emailField` refuses counts as none (spec §2 #11 then refuses a new account), and a name or username longer than its 255-character column is cut to 255. The email is checked whole before any cut (a 256-character `…@corp.example.org`, which AD's `mail` allows, would otherwise read as the different, valid-looking `…@corp.example.or`), so an over-long address counts as none.
- The first value of a multi-valued attribute is used, as Keycloak (`federation/ldap/.../LDAPObject.java:182-192` at `keycloak@c7de391a`: "Case-insensitive", "Returning just first value"), Grafana (`pkg/services/ldap/helpers.go:31-44` at `grafana@7b702d79`), GitLab (`lib/gitlab/auth/ldap/person.rb:71-92` at `gitlabhq@0739b8bf`) and LibreChat (`api/strategies/ldapStrategy.js:114-115` at `LibreChat@e1dfc104`) do. RFC 4512 §2.5 and §1.4 govern the names: "Both <attributetype> and <option> productions are case insensitive" (§2.5, "Attribute Descriptions"), and an attribute type's short name is `descr = keystring` (§1.4, a letter then letters, digits and hyphens).
- A value that is not valid UTF-8 counts as none: `firstValue` decodes with the fatal `TextDecoder` (MDN `TextDecoder` `fatal`), as `canonicalKey` does. The hub follows ldapts' own text/binary split (`src/Attribute.ts#L66-L74` at `ldapts@b38cfc3`) and RFC 4517's UTF-8 Directory String, so a value that does not decode is not text; Directus decodes lossily, which the hub does not follow, because a name with U+FFFD would be shown and searched as is.
- The cut to 255 is the hub's own choice, not a reference practice. The name and `directory_username` are display and search fields (the account links by `directory_id`, decision o), so a cut never mis-links an account, while a refusal would lock out a person whose directory name runs long (AD's `displayName` allows 256). The email is checked whole and refused when too long. Practice is mixed: Nextcloud fits directory-derived names to its column (`nextcloud/server@c4b2643a:apps/user_ldap/lib/Access.php`), GitLab refuses an over-long username (`lib/gitlab/auth/o_auth/user.rb:267-268`, `MAX_USERNAME_LENGTH = 255`) and Mattermost refuses an over-long first name (`RuneCountInString > 64`, `server/public/model/user.go` at `mattermost@4d94455a`), and Keycloak, Grafana and Gitea (`go-gitea/gitea@c0a8eb8e`, `services/auth/source/ldap/source_search.go:372-375`) pass the value on uncut. The hub cuts by code points, never splitting a surrogate pair (MDN string iterator), because MySQL 8.4 counts VARCHAR length in characters ("declared with a length that indicates the maximum number of characters you want to store", "The CHAR and VARCHAR Types"), which Nextcloud's byte `substr` does not respect. The group name is cut to 255 code points too, at one exported helper used by `entry.ts`, `sync.ts` and `admin.ts`: authentik stores `Group.name` as an unbounded `TextField` (`authentik/core/models.py:191` at `authentik@a40205dc`), Keycloak maps it with a plain `@Column` and no cut (`GroupEntity.java:67-69` at `keycloak@c7de391a`) and Mattermost refuses a display name over `GroupDisplayNameMaxLength = 128` (`server/public/model/group.go:23,208` at `mattermost@4d94455a`), so the cut is again the hub's own.
- **p. One connection per client.** ldapts documents `createConnection` and `createSecureConnection` as factories that "may be invoked more than once" because the client "transparently reconnects when it is used after being unbound or after the server closes the connection" (README "Custom connection factories"); after StartTLS that reconnect is plain TCP (`src/Client.ts:219-221, 889-935` at `ldapts@b38cfc3`; spec §6.2). The hub's factories allow one call per client, so a reconnect fails instead of sending a password in clear, in every mode. With one client per sign-in or per sync (spec §6.2), a legitimate second connection never happens (`library-apis.md` §7). Pinned by a unit test that calls each factory ldapts was given twice (Node's `net.connect` and `tls.connect` faked), a refused StartTLS that binds nothing, and `connection.ldap.test.ts`, which unbinds a live client and searches again in each mode (the pre-flight's mutation, the factories replaced by `net.connect`/`tls.connect`, passed every test before them).
- **q. Failures are classified by phase.** Before the service account is bound (connect, TLS, StartTLS, the bind), a result code is `DirectoryRefusedError` and anything else `DirectoryUnavailableError`. During the work, a result code passes through (the directory answered: wrong password, no such base, size limit), and any other error with the client no longer connected is `DirectoryUnavailableError` (ldapts destroys the socket on an operation timeout, `src/Client.ts:1096-1103`); any other error passes through as the bug it is. The CA file is read before the client exists, so a missing file is a configuration error, not an unreachable directory. The split between a directory that answered and one that did not matches Grafana (only result code 49 becomes `ErrInvalidCredentials`; every other error is returned as an error, `pkg/services/ldap/ldap.go:569-580` at `grafana@7b702d79`), passport-ldapauth under LibreChat (49 and 32 are login failures, "Other errors are (most likely) real errors", `strategy.js:281-306` at `f159fd92`) and Mattermost (one `invalid_password` id; any other LDAP failure, "LDAP unreachable, transient error", is a separate outcome that refunds the failed-attempt slot, `authentication.go:250-273` at `mattermost@4d94455a`). No reference splits by phase; the phase rule is this plan's own and is justified by the ldapts code cited above.
- An unreadable `LDAP_CA_FILE` names the setting (final review I1, Task 16's fix wave). The connection reads the file through `readCaFile` (`lib/directory/connection.ts`), which wraps a failed read in a `DirectoryConfigError` (`lib/directory/errors.ts`), and `describeError` logs it as `{ name: 'DirectoryConfigError', setting: 'LDAP_CA_FILE', cause: { code: 'ENOENT' } }`: the read's `code`, never the path, which Node's error carries in `path` and in its message (Node "Class: SystemError": `path`, "If present, the file path when reporting a file system error"; the OWASP Logging Cheat Sheet lists file paths among the data that "may also need to be treated in some special manner before the event is recorded"). The sign-in still answers `Default`, the sync records `internal_error` and the groups route answers 500: no new vocabulary. The start reads the file once as well, with the schedule on or off (`startDirectorySchedule`, only for `ldaps` and `starttls`, as the connection does), and logs the same line under `directorySchedule`, so a mis-set path shows before anyone signs in. Authelia and Keycloak load their trusted certificates at start and report a file they cannot read there (`authelia@2ed18389:internal/utils/crypto.go:373-374,389-390` with `internal/commands/root.go:85-98`; `keycloak@c7de391a:quarkus/runtime/src/main/java/org/keycloak/quarkus/runtime/KeycloakRecorder.java:190-214` with `services/src/main/java/org/keycloak/truststore/TruststoreBuilder.java:269-300`), and Grafana returns the read's error from each connection (`pkg/services/ldap/ldap.go:100-104,304-316` at `grafana@7b702d79`, Go's `*fs.PathError`). Their messages carry the path, where the hub names the setting, and unlike Authelia and Keycloak the hub keeps starting (decision ai), so local sign-ins keep working.
- **r. TLS options:** TLS 1.2 or later (`minVersion`), the CA from `LDAP_CA_FILE` when set (Node `tls.connect` `ca`: "the default list would be completely replaced"), `host` always and `servername` for a host name (Node: `servername` "must be a host name, and not an IP address"; with `socket`, `host` is still used "for certificate validation", the StartTLS case). Node then checks the certificate against that name (`checkServerIdentity`); nothing turns that off (spec §6.2). `rejectUnauthorized: true` is set explicitly, because `NODE_TLS_REJECT_UNAUTHORIZED=0` changes only that option's default (Node `tls.connect`: `rejectUnauthorized` "If not `false`, the server certificate is verified … Default: `true`"; the CLI docs: "If value equals '0', certificate validation is disabled for TLS connections"; probed on Node 22: without it, an untrusted server connected with `authorized=false`); `docs/ldap.md` says the hub ignores that variable for the directory (Task 15).
- **s. Every search names its limits.** The login search `sizeLimit: 2` (two means ambiguous, spec §6.3 step 3); a lookup by key `sizeLimit: 2`; the admin's group search `sizeLimit: 20` (spec §6.5); the membership test `scope: 'base'` with no attributes (`['1.1']`, RFC 4511 §4.5.1.8: "A list containing only the OID "1.1" indicates that no attributes are to be returned"); the user listing and member searches `paged: { pageSize: 500 }` and **no** `sizeLimit`, since ldapts accepts a size-limit result as complete whenever `sizeLimit` is set (`src/Client.ts:795`; `library-apis.md` §1), so a server-side cap fails the sync instead of cutting it short.
- `withDirectory` releases a dead connection without waiting. During the work, a non-result-code error with the client no longer connected, or with one of the hub's recorded sockets destroyed (Node `net.Socket#destroyed`), is `DirectoryUnavailableError`: the hub's own socket factories record the sockets they return, because ldapts gives no code after a reset mid-operation. When a recorded socket is already destroyed, `withDirectory` skips `unbind()` and destroys the remaining recorded sockets; before, a dead StartTLS connection made `finally`'s `unbind()` wait the 15 s operation timer (measured: RST 15,012 ms to 5 ms, FIN 15,194 ms to 3 ms). This departs from spec §6.2's "`unbind()` in `finally`" only where the connection is already dead; RFC 4511 §4.3 says "The function of the Unbind operation is to terminate an LDAP session", which a dead connection has already ended. The sentences for the record: a connection reset or closed during the work is "the directory is unreachable", as n8n classes `ECONNRESET` and the TLS certificate codes as connection errors (`ldap.service.ee.ts:50-62,406-419` at `n8n@5b78e8b6`), Directus sends every non-credential error to a 503 (`api/src/auth/drivers/ldap.ts:362-383` at `directus@8e140f94`), and go-ldap fails a pending request with "Network Error" (`v3/unbind.go:39-42` at `go-ldap@e614cf99`); ldapts' own `unbind()` returns when it is no longer connected (`src/Client.ts:750-765` at `ldapts@v9.2.0`), go-ldap's returns `ErrConnUnbound` on a closing connection (`v3/unbind.go:22-25`), Grafana closes its connections without an unbind (`pkg/services/ldap/ldap.go:170-176` at `grafana@7b702d79`), and Directus ignores a failed unbind (`api/src/auth/drivers/ldap.ts:333-343`).
- A directory error's cause is logged by name, code and message, never as the error object, as n8n logs `{ message: e.message }` for LDAP failures (`ldap.service.ee.ts:322-327,349-354` at `n8n@5b78e8b6`), Grafana logs the error value through its structured logger (`pkg/services/ldap/ldap.go:538-545` at `grafana@7b702d79`) and Directus keeps only the message (`api/src/auth/drivers/ldap.ts:371-376` at `directus@8e140f94`). A TLS name mismatch is logged with Node's own message, which names the configured host and the certificate's names (no secret).
- The group search sorts with `Intl.Collator('en')` (CLDR root order; MDN `localeCompare`: without `locales` the runtime's default locale decides), as Grafana sorts with `new Intl.Collator('en', …).compare` (`packages/grafana-data/src/field/fieldComparers.ts:54-56` at `grafana@7b702d79`) and Mattermost sorts groups with an explicit locale whose default is `'en'` (`mattermost-redux/src/utils/group_utils.ts:41-55`, `constants/general.ts:71` at `mattermost@4d94455a`); only a browser-side sort, such as Backstage's catalog table (`plugins/catalog/src/components/CatalogTable/columns.tsx:52-56` at `backstage@75128025`), leaves it to the runtime. Mattermost's `numeric: true` collation was not taken: it changes an admin list's order for no stated need.
- `LDAP_ID_ATTRIBUTE` must be unique and never change for an entry (`objectGUID`, `entryUUID`, or a directory's own unique id): a lookup by a shared value finds two entries and answers "not found" (`findGroupByKey` answers null for two entries sharing a key).
- A group base or filter that holds none of the linked groups is not a stop (spec §6.4 step 4 treats "not found" as "no members"); see the consequences.

### The sync and its schedule (Tasks 10 and 11)

`lib/directory/{plan,sync,schedule}.ts`, `instrumentation.ts`.

- **ab. A pure plan, then the writes.** The reconciliation is computed by pure functions from the hub's accounts and the directory's entries, then applied; the pure part carries the safety stops and has its own tests. n8n's LDAP sync does the same: `getUsersToCreate`, `getUsersToUpdate` and `getUsersToDisable` compute the sets that `processUsers` then writes (`n8n-io/n8n@5b78e8b6:packages/cli/src/modules/ldap.ee/ldap.service.ee.ts:430-433, 506-572`; `helpers.ee.ts:170-200`); Backstage's LDAP module reads, transforms, then applies the whole state (`backstage@75128025:plugins/catalog-backend-module-ldap/src/processors/LdapOrgEntityProvider.ts:274-317`); Keycloak reports counters per run (`keycloak@c7de391a:server-spi/src/main/java/org/keycloak/storage/user/SynchronizationResult.java:25-30`). Neither n8n nor Backstage has an empty-result stop in that path (an empty search disables every n8n LDAP account), so the spec's stops live in the plan (`ad-and-reference-projects.md` B.5).
- **ad. A group whose lookup failed is left whole.** When one of a hub group's links errors, none of that group's directory memberships change (spec §6.4 step 4 "leave that group's memberships untouched"); a group with no link left loses its directory members (decision f).
- **af. Everything is read before anything is written.** The paged user search, every linked group's lookup and member search run on one connection (spec §6.2: one client per sync), and only then do the accounts and memberships change; any connection, TLS, bind, search or page failure in that phase fails the run with nothing written (spec §6.4 step 2, GitLab's warning that "All users are blocked if the LDAP server is unavailable when an LDAP user synchronization is run", `gitlabhq@0739b8bf:doc/administration/auth/ldap/ldap_synchronization.md:196-200`). A linked group's own result-code error (the directory answered, for that group) is that group's error only (spec §6.4 step 4); a transport failure there fails the run. The hub's `ldap` accounts are read first, the directory afterwards (spec §6.4 step 3 does not fix the order). The order is the hub's own: no project in this study addresses a sign-in that changes an account while a sync is running. authentik reads the whole directory and marks local connections first and only then reads the unmarked local rows to delete them, with no guard for a connection created in between (`forward_delete_users.py:27-54` at `authentik@a40205dc`); Keycloak and GitLab read the local user for each entry or user at the moment they decide (`LDAPStorageProviderFactory.java:755-777` at `keycloak@c7de391a`; `lib/gitlab/auth/ldap/access.rb:43-65` at `gitlabhq@0739b8bf`), and every lock in the study (authentik `tasks.py:67-71`, Keycloak `UserStorageSyncTask.java:159-188`, Mattermost `job_store.go:81-135`) excludes a second sync, not a sign-in. The hub therefore reads its own `ldap` accounts first and the directory afterwards, so that an account a concurrent sign-in creates or reactivates is never judged against a directory answer older than its change. A sign-in during the write phase is still possible under either order; the reconciliation is idempotent and the next run corrects it. The hub's directory memberships are read in the same snapshot, before the directory (P3-M8 and Task 10 review I1): a first sign-in during the read phase keeps its new memberships, because the plan removes only rows it saw, and the add path is idempotent for a row a sign-in inserted meanwhile (Task 9's row-by-row retry skips a duplicate). The deactivation write is itself conditional on the current state (`eq(users.source, 'ldap'), inArray(users.id, part), isNull(users.directoryDeactivatedAt)`), the re-check the audit suggested. The summary line counts the entries the sync could not read a key from (`unreadable=<n>`), and a failing prune never changes a run's outcome.
- **ag. No run starts while another is going, whatever its trigger.** Before it claims its slot, every run (scheduled, startup or manual) checks for a run that started less than 30 minutes ago and has not finished, and skips; the slot's unique key then stops a second container. Keycloak runs every sync, scheduled or manual, through one cluster-wide key with a timeout of at least 30 seconds and answers "Synchronization ignored as it's already in progress" (`keycloak@c7de391a:model/storage-private/src/main/java/org/keycloak/storage/UserStorageSyncTask.java:159-188`); Mattermost's `SaveOnce` inserts a job only while none of its type is pending or in progress (`mattermost@4d94455a:server/channels/store/sqlstore/job_store.go:81-135`). The spec names the check for Sync now; a check and then an insert can still race, which the idempotent reconciliation absorbs (spec §6.4 "Claim"; `ad-and-reference-projects.md` B.4).
- **ah. A failed run records the counts it reached**, so a write phase cut by a database error shows what it changed; the reconciliation is idempotent and the next run completes it (spec §6.4 "Claim"). Keycloak counts added, updated and failed users per user and per page and carries on past one failed user (`SynchronizationResult.java:25-30`, `LDAPStorageProviderFactory.java:688-710,755,804-806` at `keycloak@c7de391a`), but when the run itself throws it logs and returns an empty result (`UserStorageSyncTask.java:73-77`), losing the counts; authentik keeps each finished page's `Synced N objects.` and marks the failed page's task as an error while the earlier pages stay written (`authentik/sources/ldap/tasks.py:144-176` at `authentik@a40205dc`), and Mattermost's job server marks the job `error` with the error text on the same row, whose data stays (`server/channels/jobs/jobs.go:229-262` at `mattermost@4d94455a`). All of them rely on the next run to finish the work, as the plan does; GitLab keeps logs only (`ldap-troubleshooting.md:871-877` at `gitlabhq@0739b8bf`), and its worker source is EE and was not readable.
- **ak. A scheduled run's slot is the minute it fires** (`schedule:2026-10-09T13:00Z`, spec §3.2's example), a startup run's the missed due minute (`startup:…`), so two containers starting together claim the same catch-up slot once. The slot is read at fire time (`new Date()` in the callback, Task 11); croner never fires before the due time (`dist/croner.js` `_checkTrigger` triggers only when `now >= due`, else it reschedules), so each container reads its own due minute, and only an event-loop stall of about a minute could give two containers two slots, which the running guard (decision ag) and the idempotent reconciliation cover (pre-flight 2026-10-10, part 4).
- **ai. `register()` never throws.** Next 16.3.4 rethrows a failing `register()` as "An error occurred while loading instrumentation hook" and the server does not start (`node_modules/next/dist/esm/server/lib/router-utils/instrumentation-globals.external.js`; `library-apis.md` §5); the schedule's start catches and logs its own failure, so a bad `LDAP_*` block still fails at the first request with the variables' names (spec §7.1). Formbricks wraps its start the same way (`formbricks@27ca48e2:apps/web/instrumentation.ts:38-67`, `void registerRecurringJobs().catch(…)`). A throw out of the schedule's start is logged through `describeError` (final review M9), so its cause stays readable without a secret; `lib/error-log.ts` imports ldapts, so `register()` imports it after the runtime check, as the guide's conditional import shows, and if it cannot load either, the error's name is logged.
- **aj. croner runs the callback's promise under `protect` and reports through `catch`.** croner skips a due run only while the previous callback's returned promise is pending (`protect`; `croner@adc86215:src/croner.ts:518-552, 576-596`), so the callback returns `runSync`'s promise; without `catch` a failing run becomes an unhandled rejection (`:527-540, 586-587`), so `catch` routes it to `logActionError`. `unref: true` (croner README options: the timer does not keep the process alive), so the process exits on SIGTERM when Next stops serving; a run cut there is idempotent and repeated by the startup catch-up or the next slot (spec §13).
- Entries the sync cannot read a key from are counted and named by number in the summary line (`unreadable=<n>`), so a wrong `LDAP_ID_ATTRIBUTE` that empties the result shows why; the outcome stays `empty`. Keycloak counts an entry without its UUID attribute as a failed import ("User returned from LDAP has null uuid! Check configuration …", `LDAPUtils.java:196-201`, `LDAPStorageProviderFactory.java:804-806` at `keycloak@c7de391a`) and authentik logs each one it skips ("Uniqueness field not found/not set in attributes", `authentik/sources/ldap/sync/users.py:69-79` at `authentik@a40205dc`). Logging each skipped entry's DN at debug level, as they do, was not taken: it would put names in the log against the Logs constraint (OWASP Logging Cheat Sheet, "Data to exclude").
- The prune of runs older than 90 days is housekeeping: its failure is logged and never changes a run's outcome; the summary line is written before `finishSyncRun`, whose failure is logged and rethrown. n8n's pruning logs "Failed to hard-delete executions" and carries on (`executions-pruning.service.ts:89-97,135-146` at `n8n@5b78e8b6`) and Mattermost's job cleanup logs "Error while cleaning up jobs" (`server/channels/app/server.go:1481-1493` at `mattermost@4d94455a`); the summary line is written before the run row, unlike n8n, which saves the row first (`ldap.service.ee.ts:470-494`), so a failed write keeps its summary.
- The schedule's job is built with `mode: '5-part'` like `lib/env.ts`, and a process that starts inside a due second runs that slot (croner `job.match(date)`, documented). croner's `timezone` is documented as an IANA string; the offset form that Intl accepts is not documented, which is why the zone is IANA only.
- `runSync` catches every directory failure and records it with a fixed code (`directory_unreachable`, `bind_refused`, `search_failed`, `internal_error`); a database failure in the claim, the guard, the finish or the prune propagates out of it, and its callers (the schedule and Sync now) catch it.

- OpenLDAP's LDAPS port 16360 stays published for manual checks; no test uses it (Task 4 review M6, deferred).

### Deviations from the spec text

1. The record is ADR-0029, not ADR-0028 (spec §10): the sidebar took 0028.
2. The run table's trigger column is `run_trigger` (`TRIGGER` is reserved in MySQL 8.4; spec §3 asks that names avoid reserved words), and the table also counts `group_errors` (spec §6.4 step 4, "count the error").
3. A key is binary when the id attribute is `objectGUID` (decision m), where spec §6.3 step 6 reads binary-ness from the value's length. The results are the same for `objectGUID` and `entryUUID`.
4. `servername` is set only for a host name (decision r), not for an IP address (spec §6.2 lists it among the TLS options): Node refuses an IP address there ("must be a host name, and not an IP address"; DEP0123) and checks the certificate against the host either way.
5. The `empty` safety stop is proven by `pnpm test:ldap` and the unit tests, not by Playwright (spec §8 lists it under Playwright): the e2e app's settings are fixed for a run (ADR-0010: no test switches in product code), so no spec can point it at an empty base.
6. A directory that refuses the connection answers `DirectoryUnavailable` (decision u): a refused service bind or StartTLS, and 8, 13, 51 or 52 on the person's bind, besides spec §7.3's connection, timeout and TLS failures; a domain controller that enforces LDAP signing would otherwise tell every person to check their password.
7. No run starts while another is going, whatever its trigger (decision ag; spec §6.4 names the check for manual runs).
8. The directory tab's failure text names the username (`auth.directory_login_failed`, the spec's "Check your username and password"); the local tab keeps its "Check your email and password" (`auth.login_failed`), where spec §7.3 names one key for both (decision z).
9. A binary key reaches the directory as a filter object (decision m), where spec §6.4 step 4 and §7.2 say "every byte escaped": ldapts 9.2.0 cannot carry bytes from 0x80 up through a string filter (ldapts issue #104).
10. The groups page's directory search is a GET Route Handler (decision al), where spec §6.5 names a Server Action.
11. The `users_source_credentials` CHECK also requires `directory_id_attribute IS NOT NULL` on an `ldap` row, stricter than spec §3.2's text (Task 1's review; see the data model above).

Also not as the plan's text read, by the run's rulings: `directory_unavailable` is not an `ActionErrorCode` and `user-errors.ts` has no such mapping (Sync now never throws a directory error: `runSync` records every failure in the run), so B3b adds only `sync_running` to `lib/action-result.ts`; the `admin_groups` locale key for the route's 503 stays.

### Consequences

- Good, because a directory account can never take over a local one: a first sign-in whose email any account uses is refused, and the link is the entry's key, so its Dify history (`users.id`) survives renames and moves.
- Good, because an unreachable directory, an empty answer or a changed id attribute changes nothing (the safety stops), and the sync writes only what the directory owns, so it never undoes an admin's decision.
- Good, because one suite that needs no CI proves the AD and the generic paths in all three transport modes (`pnpm test:ldap`).
- Good, because every refusal that concerns an account answers one generic message in a floor of time, and a failed sign-in logs a fixed reason, never a secret.
- Bad, because `LDAP_ENCRYPTION=none` sends every directory password, and the service account's, in clear (spec §13). It also ends when a domain controller starts requiring LDAP signing: a new Windows Server 2025 domain does by default, and so does a domain controller upgraded to 2025 that had no signing policy ("No server policy set: if no LDAP server signing policy exists, Windows Server 2025 requires LDAP signing by default", Microsoft Learn, "LDAP signing overview for Active Directory Domain Services"). Every sign-in then answers "the directory is unreachable" and the log names result code 8.
- Bad, because failed binds through the hub count toward the directory's lockout until throttling exists (spec §12), and each refused attempt with a known username costs 1 + 2·N service searches (N distinct linked groups, resolved before the person's bind, spec §6.3 step 4): input for the throttling design.
- Bad, because a code 8, 13, 51 or 52 on the person's bind answers "the directory is unreachable", unpadded, only after the search found the username, so on a directory that lets the service account bind but requires TLS for some accounts the answer tells existing usernames apart. A 51 or 52 on the group lookup or the membership test is the same (they occur only after one entry matched). A domain that requires signing refuses the service bind first, so everyone gets that answer.
- Bad, because a wrong but non-empty filter deactivates the people it misses until the next correct sync (spec §13), and a group base or filter that holds none of the linked groups is not a stop: every link turns missing and loses its directory members, and the groups page shows the missing links.
- Bad, because the in-process schedule is reference-project practice where Next's docs are silent, and the test servers cover Samba's AD, not Microsoft's (paging above 1,000, referrals, signing policy), so the owner's live check is the real test.
- Bad, because the inherited forgot-password handler can issue a reset link to a directory account's email when SMTP is on, and the reset write is refused by the CHECK (error 3819), so the handler answers its existing failure (R2 keeps both handlers as inherited; ADR-0024 deviation 6).
- Neutral, because the e2e suite runs with the LDAP block on, so every spec sees the login tabs, and the run table keeps 90 days.

## Pros and Cons of the Options

### ldapts

- Good, because it is maintained, typed, pure JavaScript and used by n8n and Backstage.
- Bad, because a binary value in a string filter is not carried (ldapts issue #104), so keys travel as filter objects (deviation 9), and its filter parser closes one missing final parenthesis silently (decision b).

### ldapjs and its wrappers, `ldap-native`, `ldap-authentication`

- Bad, because ldapjs is decommissioned, `@infisical/ldapjs` is a vendor's republish, `ldap-native` is a new native build by one author, `passport-ldapauth` is a Passport strategy on ldapjs, and `ldap-authentication` adds a maintainer for flow the hub must own.

### croner from `instrumentation.ts` with a slot claim

- Good, because it needs no extra container, no Redis and no public route; several hub containers each run a slot once through the unique index.
- Bad, because Next's docs are silent on long-lived timers in `register()` (reference-project practice only), and a run cut by a restart is repeated by the next slot.

### An external cron, a worker container, a job queue

- Bad, because a secret route is a public endpoint to guard, a worker container doubles the deployment, and a queue needs Redis.

### Linking by key

- Good, because the key never changes when a person is renamed or moved, and no email edit can take over an account.
- Bad, because changing `LDAP_ID_ATTRIBUTE` after accounts exist is unsupported (the sync stops with "ID attribute changed").

### Linking by DN, email or login name

- Bad, because each changes in ordinary directory operations, and email-linking is the account takeover the drivers rule out.

### A second Credentials provider and one form per tab

- Good, because each tab states what it asks for, the two password fields never coexist, and the providers' failures stay separate.
- Bad, because a person must know which tab to use (the directory tab opens first, except after a password change or first run).

### One form that tries both

- Bad, because an email and a username share one field, which blurs the generic message and the lockout accounting.

### A response-time floor

- Good, because an unknown username answers in the time of a wrong password (OWASP "Authentication Responses").
- Bad, because every refusal waits at least 250 ms, and AD's wrong-password timing against the floor is the owner's live check.

### A dummy bind, or nothing

- Bad, because a dummy bind would not time like a wrong password on AD, and nothing leaves the difference observable.

### Two test directories (smblds and OpenLDAP)

- Good, because AD's behaviour (`objectGUID`, `userAccountControl`, `memberOf` chains) and the generic path are both proven in all three modes.
- Bad, because they need Docker and memory (measured), and Samba is not Microsoft's AD.

### OpenLDAP only, or smblds only

- Bad, because the AD defaults would be unproven, or the generic path would be.

### Committed test certificates

- Good, because there is no test-time generation, no devDependency and no drift from a reused container.
- Bad, because key material sits in the repository (test-only; `.dockerignore` keeps `e2e/` out of the image).

### Generated certificates

- Bad, because they add a devDependency or a container step and drift from a reused container.

### A GET Route Handler for the group search

- Good, because a read needs no queue and the docs point reads to a Route Handler.
- Bad, because it adds a public HTTP endpoint that must check the session and role itself, and an entry to `app/api`.

### A Server Action for the group search

- Bad, because Server Actions are queued and "not recommended for data fetching".
