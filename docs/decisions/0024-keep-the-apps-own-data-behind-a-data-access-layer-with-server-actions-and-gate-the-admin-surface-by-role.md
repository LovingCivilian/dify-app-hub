# Keep the app's own data behind a Data Access Layer with Server Actions, and gate the admin surface by role

## Context and Problem Statement

After B1 ([ADR-0023](0023-build-the-dify-layer-as-one-route-per-operation.md)) the apps admin ran on a `server-only` Data Access Layer (DAL) with thin Server Actions, but the rest of the app's own data still sat in upstream's Route Handlers: `app/api/users/route.ts` and `app/api/users/[id]/route.ts` (list, create, update, delete) and `app/api/init/route.ts` with `app/api/init/status/route.ts` (first run). They checked only `!session`, because no role existed: every signed-in account could open the admin pages and call every admin action. They answered Chinese `message` strings, destructured request bodies without a schema, and kept the revoked-session gap of [ADR-0006](0006-require-login-everywhere-and-use-the-email-as-dify-end-user-id.md): a revoked token reached them until its cookie was re-issued. The proxy fetched `/api/init/status` over HTTP on page requests to send a fresh install to `/init`. The account menu had no password change.

Next's guides set the shape. `02-guides/data-security.md` recommends one data approach ("choosing one data fetching approach and avoiding mixing them"), a DAL that returns DTOs for new projects, and, for mutations, a `server-only` DAL that holds authentication, authorization and database logic "while `"use server"` actions stay thin" ("Using a Data Access Layer for mutations"). `02-guides/authentication.md` checks the session, then the role ("Authorization"), and gives the proxy the optimistic check only: it reads the session from the cookie and avoids database checks ("Optimistic checks with Proxy"). The charter (`docs/superpowers/specs/2026-10-07-backend-rework-charter.md` §2, §4.2, §5) settled the DAL with actions, the deleted handlers and a minimal role for B2. How should accounts, first run, the password change and the role gates be built so that a `user` account is turned away from every admin entry point?

## Decision Drivers

- One data approach (the data-security guide). `app/api` keeps only what must be an HTTP endpoint (charter §5, B2 "done when": `auth`, `health`, `dify`, `apps/[appId]/icon`).
- A role check at every entry point a request can reach directly. Action ids sit in the static JS chunks, a layout does not re-render on navigation (authentication guide, "Layouts and auth checks"), and an account can be demoted while it is signed in.
- A demotion, an email edit or a password change takes effect without waiting for the 30-day token to expire.
- Documented APIs only ([ADR-0002](0002-use-documented-library-approaches-only.md)); no new dependency (zod is [ADR-0025](0025-validate-with-zod.md)'s).
- The hub is an internal app: most accounts will come from LDAP (B3), the few local accounts are created by the owner or an admin, and SMTP is not set up (owner, 2026-10-08).

## Considered Options

1. A `server-only` DAL with thin Server Actions; the role in the next-auth JWT, refreshed from the account row on every request; the admin surface gated in the layout, the pages, the actions and the DAL.
2. Keep the Route Handlers beside the new actions.
3. Write the role into the JWT at sign-in only.
4. next-auth's database session strategy.
5. Two roles (`admin`, `user`) with a last-admin rule, the charter's design.

## Decision Outcome

Chosen option: 1, with three roles (owner, admin, user) in place of option 5's two (owner's decision, 2026-10-08), because it is the shape both Next guides describe, it closes the revoked-session gap by removing the handlers, and the per-request role refresh rides on the query that already re-checks `sessionVersion`.

- **Data.** `lib/data/users.ts` (`listUsers`, `createUser`, `updateUser`, `deleteUser`, `changeOwnPassword`; the rules `createRefusal`, `updateRefusal`, `deleteRefusal` as pure functions; `UserDto` with ISO dates, never the hash or `sessionVersion`) and `lib/data/setup.ts` (`hasAccounts`, `createOwner`) join `lib/data/apps.ts`. Every users and apps function takes the verified `actor: SessionUser` first; the apps writes (`createApp`, `updateApp`, `deleteApp`, `syncApp`) and every users function except `changeOwnPassword` call `assertAdmin(actor)` themselves. `getApp` is deleted (no caller).
- **Session.** `types/next-auth.d.ts` is a module augmentation (`User` and `JWT` carry `role`; `Session.user` carries `id` and `role` beside next-auth's defaults). `lib/auth/options.ts` exports `authorizeCredentials` (the Credentials provider's `authorize`, which selects the role with the hash) and the callbacks: on sign-in `jwt` copies `id`, `role` and `sessionVersion`; on every later call it reads `sessionVersion`, `role`, `email` and `name` from the row in one query, strips `id`, `sessionVersion` and `role` from a revoked token or a deleted account ([ADR-0018](0018-gate-route-groups-on-the-server.md)'s rule), and otherwise replaces the token's role, email and name with the row's. The `session` callback forwards `id`, `role`, `email` and `name` from the token.
- **Roles.** `lib/auth/roles.ts` (client-safe): `ROLES`, `isRole`, `hasAdminRights` (the owner or an admin), `MANAGEABLE_ROLES` (owner → admin, user; admin → user; user → none) and `canManage`. `users.role` is `enum('owner','admin','user')`, default `user`.
- **Gates.** `lib/auth/session.ts`: `verifySession()` (the account with its role, or null, also for an unknown role), `requireUser()` (the `(user)` layout and pages), `requireAdminUser()` (the `(admin)` layout and both admin pages: a `user` goes to `/apps`), `requireActor()` and `requireAdmin()` (Server Actions: `AuthError('unauthorized' | 'forbidden')`), `assertAdmin()` (the DAL). The annotation routes check the role after `resolveDifyRoute` (below, decision j). The proxy keeps only the optimistic check (`lib/access.ts`, one `PUBLIC_PREFIXES` list).
- **Actions.** `app/(admin)/user-management/actions.ts` (`createUserAction`, `updateUserAction`, `deleteUserAction`), `app/init/actions.ts` (`createOwnerAction`), `app/actions.ts` (`changePasswordAction`); the apps actions call `requireAdmin()` instead of `requireActor()`. Each validates with zod (`lib/auth/fields.ts` for name, email and password), calls the DAL, answers `ActionResult`, ends a users write in `refresh()`, and maps a throw through `toActionFailure`. `app/api/users/**` and `app/api/init/**` are deleted.
- **First run.** `/init` creates the owner through `createOwnerAction`; the login layout sends a fresh install to `/init` (`hasAccounts()`), and `/init` sends a set-up install to `/login`. The proxy makes no request of its own.
- **Password change.** The account menu (`components/shell/account-dropdown.tsx`, also inside the chat's mobile drawer) opens `components/shell/change-password-modal.tsx`. `changeOwnPassword` checks the current password, writes the new hash and bumps `sessionVersion`, which revokes every session including the current one; the client then calls next-auth's `signOut` with `/login?notice=password-changed`, and the login page shows the notice. next-auth's session `update()` is not used, since a revoked token could call it too (charter §4.2).
- **Not in this decision.** Groups, per-app access and the LDAP provider (B3, charter §5); handing ownership to another account; forgot and reset password on the DAL and actions (deviation 6).

Deviations from the charter's text, all deliberate (B2 plan header):

1. **Forms.** The charter (§2, §4.2) says `useActionState`. The users drawer, `/init` and the change-password form call their action through `startTransition` from antd Form's `onFinish`, as B1's admin forms do (ADR-0023, "Admin actions"), through the shared `hooks/use-action-transition.ts`: antd Form owns validation (`.claude/rules/frontend.md`), and Next documents an action invoked "from an event handler or `useEffect` wrapped in `startTransition`" (`02-guides/server-actions.md`; `01-getting-started/07-mutating-data.md`).
2. **One DAL module without an actor.** `lib/data/setup.ts` serves a visitor who cannot have a session, since nobody exists before the owner. Its guard is the state it checks in a transaction: the users table is empty. `users.ts` and `apps.ts` keep the actor rule.
3. **"Turned away from every admin action" (charter §4.6)** is pinned in vitest: every admin action runs with a `user` session through the real session chain (`getServerSession` mocked, `requireAdmin` real), so a test fails if an action checks only the session. e2e pins the admin pages and the admin-only Dify routes; an action id cannot be addressed from a Playwright test without reading the build's chunks.
4. **`unauthorized` in a form** shows the "session expired" message, as B1's admin forms do (`appErrorKey`), instead of navigating to `/login` as §4.5 says. The next navigation goes there through the layout or the proxy.
5. **Codes for two new refusals, inside §4.5's list.** `/init` after setup answers `forbidden`. A wrong current password answers `invalid_input` with `fieldErrors.currentPassword`, which the form shows on that field. No code is added to `ActionErrorCode`.
6. **Forgot and reset password stay as inherited (owner, 2026-10-08).** Most accounts will come from LDAP (B3) and need no reset, the few local accounts are created by the owner or an admin, and SMTP stays a future feature. B2 therefore leaves out §4.2's `lib/data/password-reset.ts`, its `requestPasswordReset` and `resetPassword` actions, and the deletion of `app/api/auth/{forgot,reset}-password/route.ts`; two of §5's "four forms" stay `fetch` forms. The forgot handler issues a link only with SMTP settings; without them no token is issued and the reset page has nothing to accept. The login page links to `/forgot-password` only when `isMailConfigured()` is true, so the link comes back by itself once SMTP is set. A forgotten local password is set again in the users drawer (decision b); nobody sets the owner's password there, so a forgotten owner password is recovered in the database (`docs/auth-gate.md` gives the recipe). §5's "done when" still holds, since both handlers sit under `auth`.
7. **Three roles: owner, admin and user (owner, 2026-10-08)**, where §2, §4.2 and §4.4 name two. The **owner** is the account `/init` creates, exactly one: it has every right, is never deleted, its role never changes, and nobody else edits it; on its own row it edits its name and email, and its password changes through the account menu. An **admin** has the owner's rights on the admin surface (apps, annotations) and manages `user` accounts; only the owner creates, edits, promotes, demotes, deletes or sets the password of an admin. A **user** is managed by the owner or an admin. One rank map decides who manages whom, for the target's current role and for the role being given (`MANAGEABLE_ROLES`); the owner role is in no list, so nothing but `/init` creates an owner. The shape is documenso's `TEAM_MEMBER_ROLE_HIERARCHY` (`packages/lib/constants/teams.ts`) checked by `isTeamRoleWithinUserHierarchy` (`packages/lib/utils/teams.ts`), where a role also manages its own rank; this line manages strictly below it, by the owner's decision. The upgrade backfill makes every existing account an admin and then the oldest (the one `/init` created) the owner, so nobody loses a right. §4.2's last-admin rule goes, since the owner cannot be removed or demoted: `last_admin` leaves `ActionErrorCode`, and the table-wide admin lock goes with it.

Decisions where the charter is silent:

- a. **The `jwt` callback refreshes `role`, `email` and `name`** from the row, in the query that already re-checks `sessionVersion`; the `session` callback forwards them explicitly (next-auth callbacks docs: token data reaches the session only through that callback). A demotion or an email change applies on the next request, and a token issued before B2 gets its role on its first use. Every `getServerSession` runs the `jwt` callback (`node_modules/next-auth/next/index.js` `getServerSession` → `AuthHandler`; `core/routes/session.js` calls `callbacks.jwt`, then `callbacks.session`). The Dify `user` (the email, ADR-0006) follows the row: when an admin edits a user's email, that user's conversations stay under the old email in Dify and drop out of their chat list from the next request (before B2, at their next sign-in). Reference projects read the row per request too: `nextjs/saas-starter`'s `getUser()`, and `create-t3-app`'s database-session template, whose session callback receives the database user. Rejected: the role at sign-in only (option 3).
- b. **Who can set a password.** In the users drawer the owner sets an admin's or a user's password, and an admin a user's (the rank map). Each such password bumps that account's `sessionVersion` (§4.2: "a password change revokes every session"). The drawer offers no password field on your own row and the DAL refuses one there (`forbidden`), so your own password changes only through the account menu, which asks for the current one. Sources: `02-guides/server-actions.md` "Security" ("Destructive operations like deletes may warrant stronger handling, such as elevated session checks or re-authentication"); `nextjs/saas-starter`'s `updatePassword` also checks the current password (`app/(login)/actions.ts`). saas-starter also refuses a new password equal to the current one, which this line does not, and does not revoke other sessions, which this line does.
- c. **Your own role is fixed** (owner, 2026-10-08), for the owner and for an admin. The users drawer disables the role field on your own row and the DAL refuses a change to it (`forbidden`). Only the owner changes an admin's role and the owner's never changes, so nobody leaves the admin area by a slip of their own.
- d. **Locking.** A users update or delete reads its target inside the transaction with a locking read on the primary key (`lockTarget`, `SELECT … FOR UPDATE`; MySQL 8.4 Reference Manual, "Locking Reads") and checks the rank against that row. A concurrent change to the same account waits for the other transaction and then reads its result, so when the owner promotes a user while an admin edits that user, the admin's write cannot rest on the stale `user` role. The lock is one row by its primary key for the few milliseconds the transaction lasts (the bcrypt hash is computed before the transaction); sign-in and the `jwt` query are consistent reads and do not wait. The actor's role comes from the session, which the `jwt` callback refreshes on every request; an action already running when its actor is demoted finishes with the role it was checked with, as every admin action does. First run takes a locking read of any users row (`lockAnyAccount`: `SELECT id FROM users LIMIT 1 FOR UPDATE`) and creates the owner only on an empty table. There, two first-run transactions hold compatible gap locks ("Gap locks can co-exist", MySQL 8.4 §17.7.1 "InnoDB Locking") and one is rolled back as a deadlock victim (error 1213), which reaches the form as `operation_failed`; at most one owner is created. That gap lock exists only under REPEATABLE READ (under READ COMMITTED "gap locking is disabled for searches and index scans", §17.7.1; "Transaction Isolation Levels"), so the transaction sets `isolationLevel: 'repeatable read'` itself (Drizzle `MySqlTransactionConfig`, `node_modules/drizzle-orm/mysql-core/session.d.ts`) instead of relying on the server's default. A unique-index refusal of the owner insert (`ER_DUP_ENTRY`) also answers `forbidden`. No surveyed reference project locks these checks, so the MySQL manual alone settles this.
- e. **Deleting a user deletes their reset tokens** in the same transaction. Nothing cascades: `password_reset_tokens.user_id` has no foreign key (`db/schema/password-reset-tokens.ts`), and MySQL deletes child rows only through a `FOREIGN KEY` constraint's `ON DELETE CASCADE` (MySQL 8.4 Reference Manual, "FOREIGN KEY Constraints": "`CASCADE`: Delete or update the row from the parent table and automatically delete or update the matching rows in the child table"). Both deletes run in `deleteUser`'s `db.transaction`, so they commit or roll back as one unit (Drizzle docs, "Transactions").
- f. **Password fields take at most 72 bytes of UTF-8** (`PASSWORD_MAX_BYTES` in `lib/auth/fields.ts`), in the zod field and as an antd rule, in the forms B2 moves to actions (users drawer, `/init`, change password; the inherited reset form keeps only its minimum). Amended in the fix wave: it replaces the plan's 128-character maximum, which accepted input bcrypt silently truncates. bcrypt reads only the first 72 bytes (bcryptjs README: "The maximum input length is 72 bytes (note that UTF-8 encoded characters use up to 4 bytes)", checked with `bcrypt.truncates(password)`), and OWASP's Password Storage Cheat Sheet ("Input Limits of bcrypt") says "you should enforce a maximum password length of 72 bytes"; so a password set through the users drawer, `/init` or the account menu is refused above 72 bytes instead of being cut. The exception is the inherited reset handler (`app/api/auth/reset-password/route.ts`, deviation 6), which checks only `password.length < 8` and so still accepts a longer password when SMTP is configured. `passwordField` refines on `new TextEncoder().encode(value).length` (zod.dev/api, `.refine`; MDN `TextEncoder.encode`: the UTF-8 encoding as a `Uint8Array`), and the three forms run the same check as an antd `validator` (`passwordBytesRule`; antd Form Rule `validator`) with the message `auth.password_too_long`; `__tests__/auth-fields.test.ts` checks both against `bcrypt.truncates` at 72 and 73 ASCII characters and 24 and 25 three-byte characters. 72 bytes is 72 Latin letters, above NIST SP 800-63B-4's "maximum password length of at least 64 characters", and fewer characters in other scripts. Sign-in and the current password of the change-password form keep no maximum, so a longer password set earlier (no form had a maximum before B2, and the inherited reset form still has none) still signs in and can be changed; the Server Action body limit bounds that input (next.config.js `serverActions.bodySizeLimit`, 1MB by default). For such a password the hub cannot meet NIST SP 800-63B-4's rule that verifiers "SHALL verify the entire submitted password (e.g., not truncate it)", since bcrypt compares its first 72 bytes only; that was already so before B2.
- g. **Error logging.** `toActionFailure` and the new `logActionError` log a database error by its driver code and errno only (`describeError` and `logActionError` in `lib/error-log.ts`, a leaf module that imports only drizzle-orm, so `lib/auth/options.ts` logs through it without the cycle `options` → `action-failure` → `session` → `options`; MDN "JavaScript modules", "Cyclic imports": "You should usually avoid cyclic imports", "Move the shared code into a third module"). Drizzle's `DrizzleQueryError` message carries the query parameters (`Failed query: … params: …`, `node_modules/drizzle-orm/errors.js`), so a failed users write would otherwise log the bcrypt hash, and a failed apps write the API key. This holds in production. In development, `db/index.ts` turns on Drizzle's query logger (`logger: env().nodeEnv === 'development'`), which prints every query with its parameters (hashes, keys, reset-token hashes) to the `next dev` console; that is pre-existing and dev-only, and a parameter-free dev logger is a recorded follow-up. Next also logs every Server Function call with its arguments in development, which printed the account forms' plaintext passwords and the apps admin's API keys to that console; `next.config.ts` sets `logging.serverFunctions: false` (next.config.js `logging`, "Server Functions": "invocations are logged by default during development. You can disable this by setting `logging.serverFunctions` to `false`"; OWASP Logging Cheat Sheet, "Data to exclude": "Authentication passwords", "Encryption keys and other primary secrets"). A database failure during sign-in is handled the same way (fix wave): next-auth puts the message of an Error thrown in `authorize` into its error URL (next-auth Credentials provider: "If you throw an Error, the user will be sent to the error page with the error message as a query parameter"), and a `DrizzleQueryError`'s message holds the SQL with the typed email. `authorizeCredentials` therefore logs the failure through `logActionError` and throws next-auth's catch-all code `Default` (next-auth Pages, "Error codes"). Refused credentials still answer `null`, next-auth's `CredentialsSignin` ("an error will be displayed advising the user to check their details"), and the login form shows "check your email and password" for that code only and its generic sign-in error otherwise (`loginFailureKey`).
- h. **User ids in actions are not checked as UUIDs** (`userIdSchema`: 1 to 36 characters). Rows that predate this line's id generator may use another format: the init migration creates `users` with `CREATE TABLE IF NOT EXISTS` and an `id varchar(191)` key (`db/migrations/20260522015811_init/migration.sql`), so an upgraded install keeps the ids upstream wrote, and the column, now `varchar(36)`, bounds only their length (MySQL 8.4 Reference Manual, "The CHAR and VARCHAR Types": the types "are declared with a length that indicates the maximum number of characters you want to store"). An unknown id answers `not_found`. App ids keep B1's strict `z.uuid()`.
- i. **`useActionTransition` moves** from `components/admin/apps/` to `hooks/` (consumers outside the apps admin: the users table and drawer, the init form, the change-password modal). `hooks/` is the conventions' root folder for shared code (`docs/frontend-conventions.md`: "Shared code lives in root folders: `components/<feature>/`, `hooks/`, `lib/`"), and a custom Hook is how React shares the logic (react.dev, "Reusing Logic with Custom Hooks": "Custom Hooks let you share logic between components").
- j. **Annotations** (the B1 carry): list, update and delete need admin rights (`hasAdminRights`); create is allowed to an account with admin rights, and to a `user` only where the app's `enableAnnotation` is on (charter §4.1; `resolveDifyRoute` now carries `annotationEnabled`). The refusal is Dify's envelope `403 forbidden` (`forbiddenResponse()`).
- k. **A stricter email check, the same in the forms.** zod 4's `z.email()` refuses an address without a top-level domain (`a@localhost`), which the inherited handlers accepted: its default regex requires dot-separated labels and a top-level label of two or more letters (zod.dev/api, "Default email regex"). antd's `type: 'email'` rule refused such addresses in the forms too (`@rc-component/async-validator` `lib/rule/type.js`), the login form's included, so only a direct request to an inherited handler could have stored one, and that account could not sign in through the form before B2 either. The count of such accounts on a copy of the owner's database is a Task 9 check (Verification). Amended in the fix wave: apart from those, the two rules disagree. antd's `type: 'email'` accepts addresses `z.email()` refuses (`user@münchen.de`, `jo#e@example.com`, `o.brien!x@example.com`), and such an address passed the form and came back as an `invalid_input` that marks no field; on `/init` that read "setup failed" on every retry. So the users drawer and `/init` check emails with the server's own field, a `validator` that calls `emailField.safeParse` (`emailRule` in `lib/auth/fields.ts`; antd Form Rule `validator`; zod `safeParse`), and agree with the action by construction, its 255-character maximum included. The login form keeps `type: 'email'`, since sign-in does not validate with zod. The name fields of the same two forms check with `nameField` in the same way (`nameRule`, fix wave round 2), so a name over 255 characters is refused on its field (`admin_users.name_too_long`, `init.owner_name_too_long`) instead of coming back as a field-less `invalid_input`; a blank name stays with the `required` rule's `whitespace` check.

### Consequences

- Good, because a `user` account is refused at every admin entry point: the `(admin)` layout and pages redirect it to `/apps`, every admin action answers `forbidden` before it reads its input, the DAL refuses again, and the admin-only Dify routes answer `403 forbidden`.
- Good, because `app/api` holds only `auth` (next-auth and the two inherited reset handlers), `health`, `dify` and `apps/[appId]/icon`, pinned by `__tests__/api-routes.test.ts`, and the `/api/users/*` revoked-session gap of ADR-0006 is closed by removal.
- Good, because a demotion, an email edit or a deleted account takes effect on the next request, a password change or reset signs every session out, and the refresh costs no query beyond the existing per-request `sessionVersion` read.
- Good, because the rank is one table (`MANAGEABLE_ROLES`) that the drawer, the table's Edit and Delete and the DAL all read; the owner always exists, so an account with every right always remains.
- Good, because the codes stay inside charter §4.5's list: `forbidden`, `cannot_delete_self` and `email_in_use` are now in use, `invalid_input` carries `fieldErrors.currentPassword`, and `last_admin` is removed from `ActionErrorCode`. The chat's `failureText` maps `forbidden` and `icon_not_found`, and the admin apps' `appErrorKey` shows `forbidden` as its own message (`common.forbidden`).
- Bad, because an admin's email edit moves a user's Dify identity: that user's earlier conversations stay under the old email and leave their chat list (decision a).
- Bad, because ownership cannot be handed to another account in the app; changing the owner is a database change, and while SMTP is unused a forgotten owner password is a database fix (`docs/auth-gate.md`).
- Bad, because forgot and reset password keep their inherited Route Handlers and `fetch` forms with Chinese messages; the inherited handlers log raw errors (a failed query in the forgot handler prints the email, the user id and the reset-token hash; one in the reset handler's token lookup prints the token hash), `/reset-password` stays reachable while signed in, and `auth.reset_title` still reads "Reset admin password". Moving them onto the DAL and actions, with the signed-in redirect, is a follow-up if local accounts ever need them.
- Bad, because in development Drizzle's query logger prints query parameters, password hashes and API keys included, to the `next dev` console (decision g).
- Neutral, because with MySQL down `/login` renders `app/(auth)/error.tsx`, since its layout calls `hasAccounts()` and Next's `error.js` "wraps `loading.js`, `not-found.js`, `page.js`, and nested `layout.js` files" (`03-api-reference/03-file-conventions/error.md`). This is not a regression: the old proxy's `/api/init/status` answered 500, the proxy redirected to `/init`, and that page threw.
- Neutral, because a fresh install no longer sends `/forgot-password` and `/reset-password` to `/init`. There is no account to reset and the handlers are unchanged; charter §4.2 names only the login layout, and deviation 6 keeps those pages as inherited.
- Neutral, because the annotation routes resolve the app before the role (session → app → role → input), so a `user` learns whether an app exists or is disabled before the role refusal. That discloses nothing new until B3 and follows B1's `resolveDifyRoute` contract; the data-security guide's DAL mutation example also reads the resource before authorizing. Once B3 filters apps per account, this order answers 404 for an app outside the account's access.

## Implementation Plan

- **Affected paths**: `next.config.ts` (`logging.serverFunctions`, decision g), `lib/auth/{roles,fields,options,session}.ts`, `types/next-auth.d.ts`, `db/schema/users.ts` and the two migrations `db/migrations/20261008125109_b2-users-role/` and `db/migrations/20261008130753_b2-users-role-backfill/`, `lib/data/{apps,users,setup}.ts`, `lib/action-result.ts`, `lib/action-failure.ts`, `lib/error-log.ts`, `lib/dify/{errors,route}.ts`, `app/api/dify/[appId]/apps/annotations/**`, `app/(admin)/layout.tsx`, `app/(admin)/app-management/{page,actions}.ts(x)`, `app/(admin)/user-management/{page,actions,schemas}.ts(x)`, `app/init/{page,actions}.ts(x)`, `app/actions.ts`, `app/(auth)/login/{layout,page}.tsx`, `proxy.ts`, `lib/access.ts`, `hooks/use-action-transition.ts`, `components/admin/users/**` (`role-labels.ts` new; `user-row.ts` deleted), `components/admin/apps/app-errors.ts`, `components/auth/{init-form,login-form,auth-failure}.ts(x)`, `components/shell/{account-dropdown,change-password-modal,account-errors,sign-out}.ts(x)`, `components/chat/hooks/dify-errors.ts`, `locales/{en,zh,ar}/translation.json`, `e2e/fixtures/users.ts`, the specs below; deleted: `app/api/users/**`, `app/api/init/**`.
- **Dependencies**: none.
- **Patterns to follow**: a new admin-only Server Action calls `requireAdmin()` first and its DAL function calls `assertAdmin(actor)`; a new admin page calls `requireAdminUser()` outside any `try/catch`; a new users write locks its target (`lockTarget`) inside the transaction and checks the rank (`canManage`, or the `*Refusal` rules) against the locked row, never against the input's role; a new admin-only Dify route checks `hasAdminRights(resolved.ctx.actor)` right after `resolveDifyRoute` and answers `forbiddenResponse()`; a form calls its action from `onFinish` through `useActionTransition` and maps the code to a translation key; an unexpected throw goes through `toActionFailure` or `logActionError`; tests of a session-bearing action mock `next-auth/next`'s `getServerSession` and `@/lib/auth/options` and keep `lib/auth/session` real.
- **Patterns to avoid**: a Route Handler for the app's own data; an admin action that calls only `requireActor()`; a DAL function without an actor outside `lib/data/setup.ts`; logging a raw database error (`console.error(error)` on a Drizzle or mysql2 error); a rank check against the role the client sends; a password field on your own row in the users drawer; a second owner created outside `/init`; reading the role only at sign-in; next-auth's session `update()` to re-validate a token.
- **Configuration**: none. SMTP stays unset; the login page reads `isMailConfigured()` (`lib/mail.ts`).
- **Migration steps**: the container's entrypoint applies both migrations on start; `pnpm dev` needs `env $(grep DATABASE_URL .env.development.local) pnpm db:migrate` by hand (`CLAUDE.md`, "Quick dev loop"). The first migration adds the column (default `user`); the second, a Drizzle custom migration, makes every existing account an admin and then the oldest by `created_at`, `id` the owner. If a hard crash leaves the `ALTER` applied but unrecorded, run `ALTER TABLE users DROP COLUMN role;` and restart (More Information).

## Pros and Cons of the Options

### A DAL with thin actions and the role refreshed per request

- Good, because it is the data-security guide's one approach and its mutation pattern, and the authentication guide's session-then-role order, with the proxy kept optimistic.
- Good, because the role check exists at every layer a request can reach, so a demoted or hand-crafted request is refused even where the UI hides the control.
- Bad, because every new admin entry point needs its own check in two places (the action or route, and the DAL), which the tests pin rather than the type system.

### Keep the Route Handlers beside the actions

- Good, because the inherited handlers already work.
- Bad, because it is the mix the data-security guide advises against, keeps the revoked-session gap and the Chinese messages, and the charter (§2) rejected it.

### The role in the JWT at sign-in only

- Good, because it needs no extra read.
- Bad, because a demoted admin keeps the admin rights until the token expires (next-auth's default session `maxAge` is 30 days, next-auth.js.org Options), and the refresh is free anyway: the `jwt` callback already reads the row for `sessionVersion`.

### next-auth's database session strategy

- Good, because the session row is the source of truth and can be deleted to sign an account out.
- Bad, because it needs a session table and an adapter for what one column on `users` gives, and next-auth v4's Credentials provider "can only be used if JSON Web Tokens are enabled for sessions" (next-auth.js.org, Credentials provider), the strategy ADR-0006 and ADR-0018 build on.

### Two roles with a last-admin rule

- Good, because it is the charter's minimal design.
- Bad, because the last-admin rule needs a table-wide lock on every demotion and delete, and any admin can demote or delete every other admin; one owner who cannot be removed keeps an account with every right without that lock (owner's decision, 2026-10-08).

## More Information

Details settled during B2 (each with its reason in the run's records, `.superpowers/sdd/2026-10-08-backend-b2-accounts/progress.md`):

- **The migration is two folders.** `20261008125109_b2-users-role` holds the generated `ALTER` only; `20261008130753_b2-users-role-backfill` is a Drizzle custom migration (`drizzle-kit generate --custom`, Drizzle docs "Custom migrations") holding the two `UPDATE`s; the second is a single-table `UPDATE … ORDER BY created_at, id LIMIT 1` (MySQL 8.4 "UPDATE Statement": "If the `ORDER BY` clause is specified, the rows are updated in the order that is specified. The `LIMIT` clause places a limit on the number of rows that can be updated"). `ALTER TABLE` commits implicitly (MySQL 8.4 "Statements That Cause an Implicit Commit": DDL statements "implicitly end any transaction active in the current session"), and Drizzle's migrator identifies applied migrations by name (`node_modules/drizzle-orm/migrator.utils.js`), so with the data statements in their own migration a crash re-runs only the idempotent backfill. Residual: a hard crash between the `ALTER` and its record insert inside the migrator still leaves the `ALTER` unrecorded; the recovery is `ALTER TABLE users DROP COLUMN role;`, then a restart. `users.updated_at` also gains Drizzle's `$onUpdate`, so every update of a users row through Drizzle's query builder sets it.
- **The email in the session token.** next-auth v4 carries the email in its JWT by default, and decision a keeps it current. Next's authentication guide advises against personally identifiable information such as an email address in the session payload ("Stateless Sessions"); its example signs the payload with jose's `SignJWT` (HS256) without encrypting it. next-auth v4 encrypts the token: "JWTs are encrypted by default (JWE)" (next-auth.js.org, Options) and "Since v4, all JWT tokens are encrypted by default using A256GCM" (FAQ). The cookie is HttpOnly. No custom `jwt.encode`/`decode` is written (ADR-0002).
- **No email normalisation at sign-in.** `users.email` declares no collation, so it takes the default of `utf8mb4`, `utf8mb4_0900_ai_ci` (checked on the e2e database; MySQL 8.4 "Character Sets and Collations in MySQL"), which compares case-insensitively ("Unicode Character Sets": `_ci`); the unique index enforces the same rule. Whitespace is refused by antd's `type: 'email'` rule and by `z.email()`.
- **The own password change is tied to the locked row.** `changeOwnPassword` verifies against a plain read as a fast refusal, hashes the new password, then runs a short transaction: a `FOR UPDATE` read of the row, a refusal (`invalid_input` with `currentPassword`) if the hash changed since the check, otherwise the write with `sessionVersion + 1` (MySQL 8.4 "Locking Reads": "the regular SELECT statement does not give enough protection"; decision d). A concurrent admin reset therefore cannot be overwritten by the old password's holder. The guard covers all three writers of a password: the users drawer (`updateUser`, through `lockTarget`), the account menu, and the inherited reset handler (a searched `UPDATE` by primary key takes the same exclusive lock). `nextjs/saas-starter`'s `updatePassword` does not lock, so it is no precedent here.
- **Failure logging.** `describeError` reads a `DrizzleQueryError`'s cause `code` only as a string and `errno` only as a number. mysql2 sets `code` only to fixed identifiers: the `ER_*` names of its error table (`lib/packets/packet.js`), `PROTOCOL_CONNECTION_LOST`, `ETIMEDOUT` and `PROTOCOL_ERROR` (`lib/base/connection.js`). A bare mysql2 error is reduced to name, code and errno when it carries an `errno`, the server (ERR packet) errors, which are the ones that carry `err.sql` (`lib/commands/command.js`). Any other error is logged as it is.
- **The `forbidden` envelope is defined once**, `forbiddenResponse()` in `lib/dify/errors.ts`; `errorResponseFrom`'s `AuthError('forbidden')` answers it, and `lib/dify/route.ts` re-exports it for the routes.
