# Login gate (fork)

Every page, every Server Action and every `/api/*` route outside the public list requires the account login, and the admin surface (the `(admin)` pages, the admin actions, the admin-only Dify routes) requires admin rights: the owner or an admin (ADR-0024). The one action without a session is first run, which creates the owner while no account exists. The Dify end-user id is the signed-in account's permanent id (`users.id`), set on the server (ADR-0026). This departs from upstream's dual-auth model (`docs/superpowers/specs/2026-05-13-web-dual-auth-design.md`); design: `docs/superpowers/specs/2026-10-03-login-for-all-users-design.md`; roles and the Data Access Layer: ADR-0024.

## Where it lives

- `proxy.ts` + `lib/access.ts`: the optimistic check of Next's authentication guide. `lib/access.ts` holds one public list, `PUBLIC_PREFIXES` (`/login`, `/forgot-password`, `/reset-password`, `/init`, `/api/auth`, `/api/health`, Next's assets). The proxy classifies the decoded pathname: a public path passes, a token with an `id` passes (a revoked token has none, ADR-0018), and anything else gets the 401 envelope (`{ code: 'unauthorized', message, status }`) on `/api/*` (deny by default) or a redirect to `/login?callbackUrl=` for a page. It reads only the cookie and makes no request of its own; first run is the login layout's job.
- `lib/auth/session.ts`: `getCachedServerSession()` (React `cache` around `getServerSession`, one lookup per server render), `verifySession()` (the account `{ id, email, name, role }` or null), `requireUser()` (pages and layouts: the account or a redirect to `/login`), `requireAdminUser()` (the `(admin)` layout and pages: an account with admin rights; any other signed-in account goes to `/apps`), `requireActor()` (Server Actions: the account or `AuthError('unauthorized')`), `requireAdmin()` (admin Server Actions: `requireActor()`, then `AuthError('forbidden')` without admin rights), `assertAdmin(actor)` (the Data Access Layer's own role check) and `redirectSignedInUser()`.
- `lib/auth/options.ts`: next-auth's options. `authorizeCredentials` is the Credentials provider's check: the account with its role, or null. The `jwt` callback copies `id`, `role` and `sessionVersion` at sign-in; on every later call it reads the account row once, strips `id`, `sessionVersion` and `role` from a revoked token or a deleted account, and otherwise refreshes the token's role, email and name from the row, so a demotion or an email edit applies on the next request. The `session` callback forwards `id`, `role`, `email` and `name`.
- `lib/auth/roles.ts` (client-safe): the three roles `owner`, `admin` and `user`; `hasAdminRights` (the owner or an admin); the rank map `MANAGEABLE_ROLES` (the owner manages admins and users, an admin manages users, a user manages nobody) and `canManage(actor, target)`. The owner is the account `/init` creates; no list contains `owner`, so nothing else creates one, and nobody manages their own rank.
- The layouts: `app/(user)/layout.tsx` calls `requireUser()` and `app/(admin)/layout.tsx` calls `requireAdminUser()` (ADR-0018); the pages under them call the same gate again, since a layout does not re-render on client-side navigation. `app/(auth)/login/layout.tsx` sends a fresh install to `/init` (`hasAccounts()`), then calls `redirectSignedInUser()`; `app/(auth)/forgot-password/layout.tsx` calls `redirectSignedInUser()`; `/reset-password` has no layout yet (Known limits). A revoked session has no `user.id` and is not sent on. A layout cannot read the pathname or `?callbackUrl=`, so its redirects carry none, and a signed-in visitor on `/login` always lands on `/apps`.
- The Data Access Layer (`lib/data/`, `server-only`): `apps.ts` and `users.ts` take the verified actor first. The apps writes and the users functions call `assertAdmin(actor)` themselves (except `changeOwnPassword`, which acts on the actor's own row only); `users.ts` applies the rank (`createRefusal`, `updateRefusal`, `deleteRefusal`) against the target row read under a locking read (`lockTarget`, `SELECT … FOR UPDATE`), and refuses a change to your own role or password there. `setup.ts` takes no actor: it runs on state, creating the owner only while the users table is empty (a locking read under REPEATABLE READ), and answers `forbidden` once any account exists.
- Forgot and reset password: still the inherited Route Handlers `app/api/auth/{forgot,reset}-password/route.ts` and their `fetch` forms (ADR-0024). The forgot handler issues a link only with SMTP settings; without them no token is issued, and the reset page has nothing to accept. The login page links to `/forgot-password` only when SMTP is configured (`isMailConfigured()` in `lib/mail.ts`).
- The actions files: `app/(admin)/app-management/actions.ts` and `app/(admin)/user-management/actions.ts` call `requireAdmin()` first; `app/actions.ts` (`changePasswordAction`) calls `requireActor()`; `app/init/actions.ts` (`createOwnerAction`) has no session to check and relies on `lib/data/setup.ts`. Each answers an `ActionResult` code that the form translates.
- `lib/dify/route.ts`: `resolveDifyRoute()`, the first step of every `/api/dify/*` handler: `verifySession()` (401 envelope), then the app (404, 403 when disabled); `user` for Dify is the session's account id, never the email (ADR-0026). The annotation routes then check the role: list, update and delete need admin rights, create needs them unless the app enables annotations, and a refusal answers `forbiddenResponse()` (403 `forbidden`). `app/api/apps/[appId]/icon/route.ts` calls `verifySession()` itself.
- `app/layout.tsx` → `components/providers/app-providers.tsx`: the root layout passes the cached server session to `SessionProvider`, so `useSession` has the session on first render (the account button is in the first HTML).
- `components/shell/account-dropdown.tsx` (also in the chat's mobile drawer): "signed in as" (from `useSession`), "Change password" (`change-password-modal.tsx`: the current and the new password go to `changePasswordAction`; on success every session is revoked and `signOut` lands on `/login?notice=password-changed`), and log out.

## After picking upstream commits

This line takes upstream's work by cherry-pick or re-implementation only (ADR-0022).

1. List routes that forward a user to Dify and check each uses the session value:

   ```bash
   git grep -nE "getUserIdFromRequest|searchParams.get\('user'\)|body\.user|x-user-id|\.email" -- app/api/dify lib/dify
   ```

   Expected: no output. For any hit, take `user` from `resolveDifyRoute` (`resolved.ctx.user`) instead; an `.email` hit means the email is reaching Dify, which ADR-0026 rules out (the Dify `user` is the account id).

2. New pages and new `/api/*` routes are gated by the proxy automatically. Every handler under `app/api/dify/` resolves the session first through `resolveDifyRoute` (`lib/dify/route.ts`) and sets `user` from it; new routes copy that, and an admin-only one checks `hasAdminRights(resolved.ctx.actor)` next and answers `forbiddenResponse()`. A new admin-only action calls `requireAdmin()` first and its DAL function calls `assertAdmin(actor)`. A new users write checks the rank (`canManage`) against the target row it read with `lockTarget` inside its transaction, never against the role the client sent. A new public page (if upstream adds one) goes into `PUBLIC_PREFIXES` in `lib/access.ts`, with its case in `__tests__/access.test.ts`.
3. Expected conflicts: `proxy.ts` (keep the fork's gate, re-apply upstream's additions inside it), `app/(user)/layout.tsx` and `app/(admin)/layout.tsx` (keep the fork's server gates); upstream's `app/api/client/**`, `app/api/users/**`, `app/api/init/**`, `lib/session-user.ts` and `lib/dify-client.ts` no longer exist here, so a change to them is re-implemented in `app/api/dify/**` and `lib/dify/`, or in `lib/data/` and the actions files.

## Known limits

- Conversations created before the gate (fingerprint ids) are not listed.
- The layout redirect carries no `callbackUrl` (a layout cannot read the pathname); only the proxy adds it.
- A password change or reset, or a deleted account, revokes existing JWTs, and the gates differ in when they notice. Every `/api/dify/*` route and every action rejects a revoked JWT at once: next-auth still builds a session from it, but without `user.id`, so `verifySession()` returns null. Every page under `(user)` and `(admin)` redirects it to `/login` too, on a hard load or a navigation to another page. Client-side route changes inside a group reuse the layout, so the layout catches a token revoked mid-session at the next hard load; the pages and actions re-check it themselves. The browser's cookie is not cleared: the `jwt` callback strips `id`, `sessionVersion` and `role`, and next-auth re-issues the cookie without them at the next session refresh (the tab regaining focus, or a `refetchInterval` if one is ever set). A sign-in instead writes a fresh token with `id` and `sessionVersion` (the `jwt` callback with `user`, `lib/auth/options.ts`), which replaces the revoked cookie. Until then the proxy's `getToken` still sees the old token and lets requests through to the layouts, pages, actions and handlers, which turn it away; afterwards the proxy treats it as signed out as well (401 envelope on `/api/*`, `/login?callbackUrl=` on pages).
- Sessions last 30 days (next-auth default). The root layout hands the server session to `SessionProvider`, which therefore skips its on-mount `/api/auth/session` fetch: the cookie's expiry is no longer slid forward on every page load. Renewal happens only when the tab regains focus (`refetchOnWindowFocus`, default on) or at sign-in (ADR-0018).
- The role refresh costs nothing beyond the existing per-request `sessionVersion` query: the `jwt` callback reads role, email and name in the same query.
- The Dify `user` is the account's permanent id (ADR-0026), so an email edit leaves a user's Dify history where it is, but Dify's logs and Langfuse show an opaque id: the users page's "Dify user ID" column maps it to the person and copies it, and the table search finds an account by its id. Conversations created under an email before ADR-0026 are no longer listed (a clean cut); they stay in Dify's logs and Langfuse under the email.
- Without SMTP there is no self-service reset (SMTP is a future feature, owner 2026-10-08). The owner sets a forgotten admin's or user's password in the users drawer, and an admin a user's; that signs the account out everywhere. Nobody sets the owner's password there, so a forgotten owner password is recovered in the database. Run this from the repo root, so `bcryptjs` resolves (cost 12 is `lib/auth/password.ts` `HASH_ROUNDS`). The password is read without echo, so it stays out of the shell history, and the hash reaches MySQL through an environment variable, so the shell never expands its `$2b$12$…`. On the production server, use its compose file:

  ```bash
  read -rs PW && export PW
  HASH=$(node -e "process.stdout.write(require('bcryptjs').hashSync(process.env.PW, 12))") && unset PW
  docker compose -f docker-compose.local.yml exec -T -e HASH="$HASH" mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE" -e "UPDATE users SET password = '\''$HASH'\'', session_version = session_version + 1 WHERE role = '\''owner'\''"'
  unset HASH
  ```

- Ownership cannot be handed to another account in the app; changing the owner is a database change (a transfer is a recorded follow-up).
- `/reset-password` stays reachable while signed in. B2 left the reset flow as inherited (ADR-0024), so the signed-in redirect there waits for that flow's follow-up, although the account menu now offers a password change.
- In development, Drizzle's query logger (`db/index.ts`) prints every query with its parameters, password hashes and API keys included, to the `next dev` console; production logs a database error by its driver code only (ADR-0024, decision g).
- B3 brings groups, per-app access and LDAP.
