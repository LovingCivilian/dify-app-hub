## 1. `@ag-ui/client` 1.0.2 as the hub's upstream client on a Node server

### 1.1 What the package exposes (from `dist/index.d.ts`)

- `HttpAgent` with `HttpAgentConfig { url, headers?, fetch?: (url, init) => Promise<Response> }` plus the `AgentConfig` fields `agentId, description, threadId, initialMessages, initialState, debug` (`index.d.ts` lines 21–34). The docs page shows only `url` and `headers` (https://docs.ag-ui.com/sdk/js/client/http-agent); the `fetch` option exists only in the typings.
- `HttpAgent.runAgent(parameters?: RunHttpAgentConfig, subscriber?)`, where `RunHttpAgentConfig = RunAgentParameters & { abortController?: AbortController }` and `RunAgentParameters = Partial<Pick<RunAgentInput, "runId" | "tools" | "context" | "forwardedProps">> & { resume?: ResumeEntry[] }` (`index.d.ts` lines 35–38, 300–316). `threadId`, `messages` and `state` come from the instance (constructor, `setMessages`, `setState`). `parentRunId` cannot be set through the parameters (it is not in the `Pick`); `prepareRunAgentInput()` is `protected` and documented as overridable (https://docs.ag-ui.com/sdk/js/client/abstract-agent, "Protected Methods").
- `HttpAgent.run(input): Observable<BaseEvent>`: the raw transport (`index.d.ts` line 318).
- Lower-level exports: `runHttpRequest(fetchResponse: () => Promise<Response>): Observable<HttpEvent>`, `transformHttpEventStream(source$)`, `parseSSEStream`, `parseProtoStream`, and the stream stages `enforceEvents()`, `transformChunks()`, `verifyEvents()`, plus `CompatibilityBoundary` (a `Middleware` class), `compactEvents`, `buildResumeArray`, `getRunOutcome`, `isInterruptExpired`, `enforceOutgoingInput` (`index.d.ts` lines 616–743, export list line 759).
- `events$` is listed on the AbstractAgent docs page ("Observable Properties") but is **not** a property in the 1.0.2 typings (no `events$` member on `AbstractAgent`; the name only appears as a parameter). A docs/typings mismatch: do not build on it.

### 1.2 Where the 0.x → 1.0 compatibility layer runs

- `AbstractAgent.runAgent()` builds, per run, the chain `[...this.middlewares, new CompatibilityBoundary()]` with the boundary **innermost** ("closest to the wire"), then pipes `enforceEvents → transformChunks → verifyEvents → apply (subscribers)` (`src/agent/agent.ts` lines 336–373; the comment: "The always-on inbound compatibility boundary runs innermost … Appended per run and never stored").
- `connectAgent()` has no middleware chain and applies the boundary as an operator, `compatibilityBoundaryOperator()` (`agent.ts` lines 445–453). That operator is **not exported** from the package (`src/middleware/compatibility-boundary.ts` lines 404–415; absent from the export list).
- `HttpAgent.run()` is only `runHttpRequest(...)` → `transformHttpEventStream(...)` (`src/agent/http.ts` lines 91–103): **no compatibility boundary, no enforcement, no chunk expansion, no verification**. A server that consumes `run()` directly gets the producer's raw (possibly 0.x-shaped) events.
- So the compat layer is reusable in two documented-in-typings ways: (a) `runAgent()` with a subscriber (the only path the docs describe), or (b) composing the exported pieces by hand: `new CompatibilityBoundary().run(input, httpAgent).pipe(enforceEvents(), transformChunks(), verifyEvents())`. (b) is in the typings but no docs page shows it (docs silent).
- The migration guide confirms the boundary is client tolerance, not a parser feature: "Direct schema validation remains strict and does not invoke the client's event compatibility boundary … AG-UI does not expose a public request-normalization helper" (https://docs.ag-ui.com/migrating-to-1-0, "Omit whole optional null fields").
- Outgoing input: `HttpAgent.run()` calls `enforceOutgoingInput(input)` before sending ("Unknown material is stripped with a warning; a malformed known field fails the run before a byte leaves the process", `http.ts` lines 92–101), and strips `subagentRunId: null` (`http.ts` lines 15–39). `prepareRunAgentInput` drops `activity` messages and declares `protocolVersion: "1.0"` unless the peer ceiling is pinned lower (`agent.ts` lines 578–609).

### 1.3 Getting the events one by one

- A subscriber's `onEvent({ event, messages, state, agent, input })` is called per event **after** enforcement, chunk expansion and verification, inside `concatMap(async …)` (`src/apply/default.ts` lines 180–188), so it is awaited (an async `onEvent` applies back-pressure to the stream) and can return `{ stopPropagation: true }` to drop an event. The typed per-event hooks (`onTextMessageContentEvent` with `textMessageBuffer`, `onToolCallEndEvent` with parsed `toolCallArgs`, `onRunFinishedEvent` with `outcome`/`interrupts`/`pendingToolCallIds`, …) are in `index.d.ts` lines 160–297.
- This is exactly how CopilotKit's runtime consumes an upstream `HttpAgent` on the server: `request.agent.runAgent(request.input, { onEvent: ({ event }) => { runSubject.next(event); … } })` (`packages/runtime/src/v2/runtime/runner/in-memory.ts` line 816).
- Chunk events (`TEXT_MESSAGE_CHUNK`, `TOOL_CALL_CHUNK`, `REASONING_MESSAGE_CHUNK`) reach `onEvent` already expanded into start/content/end triads (pipeline order above).
- A protocol violation (e.g. an event after `RUN_FINISHED`) is fatal in `verifyEvents`; `onError` rethrows non-abort errors, so `runAgent()` rejects after the events before the violation were delivered (`agent.ts` lines 692–750).

### 1.4 What `runAgent` returns; `pendingInterrupts`

- `RunAgentResult = { result: any; newMessages: Message[] }` (docs "Return Value"; `index.d.ts` lines 528–531). `newMessages` is `this.messages` filtered to ids that were not present before the run (`agent.ts` lines 311, 397–400): a message the producer **updated** under an existing id (e.g. a `MESSAGES_SNAPSHOT` restating history) is not in `newMessages`. `result` is `RUN_FINISHED.result` of a success outcome (lines 316–320).
- `pendingInterrupts`: "Interrupts emitted by the most recent run that have not yet been resolved" (`agent.ts` lines 123–126). Set from `RUN_FINISHED` with `outcome.type === "interrupt"`, reset to `[]` on any other `RUN_FINISHED`, only if no subscriber stopped propagation (`src/apply/default.ts` lines 1119–1137); not touched by `RUN_ERROR`.
- `onInitialize` enforces the spec's coverage rule for `runAgent` calls only: every pending interrupt must have a `resume` entry ("Thread has N pending interrupt(s) not addressed by resume"), and an expired interrupt can only be answered with `status: "cancelled"` (`agent.ts` lines 611–634). The field is public, so a stateless server that creates a fresh `HttpAgent` per request starts with `[]` and would have to restore it from its own store to get this check (**(opinion)**: the hub enforces coverage itself from its store anyway, as charter §4.3 says).

### 1.5 `abortRun()` and `AbortController`

- Docs: `HttpAgent.abortRun()` "Cancels the current HTTP request using the AbortController"; `abortController` is a public property; `requestInit()` passes `signal: this.abortController.signal` (https://docs.ag-ui.com/sdk/js/client/http-agent). `AbstractAgent.abortRun()` "Cancels the current agent execution" (abstract-agent page) but its base implementation is empty (`agent.ts` line 486). `runAgent` accepts a caller-owned `abortController` (`http.ts` lines 66–72).
- What an abort produces (source): when the reader rejects with an `AbortError` mid-stream, `transformHttpEventStream` **synthesizes `RUN_ERROR { code: "abort", message: "This operation was aborted" | "Request aborted" }`** and completes (`src/transform/http.ts` lines 113–123). An abort before the response headers rejects the fetch; `onError` classifies `AbortError` and swallows it (`agent.ts` lines 729–748). In both cases **`runAgent()` resolves** — a stopped run settles like a completed one (issue ag-ui-protocol/ag-ui#2417, open; maintainer comment 2026-10-07: "`abortRun()` is still an empty method, and `RunAgentResult` carries no outcome … That's an API change rather than a patch"; a contributor took it on to make `runAgent()` reject on truncation, so this may change in a later 1.0.x). Issue #2327 (open) records that the synthesized cancel is "indistinguishable from provider failure" except by `code: "abort"`.
- CopilotKit hit the same path with an HttpAgent proxy "(e.g. pydantic-ai's AGUIAdapter)": the abort yields a live `RUN_ERROR` with `code: "abort"` while a text message is still open (`runner/__tests__/in-memory-runner.test.ts` lines 1846–1851, issue CopilotKit#5812).

### 1.6 Re-encoding to the browser: `@ag-ui/encoder`

- `EventEncoder({ accept? })`: `encodeSSE(event)` returns `` `data: ${JSON.stringify(omitOptionalNulls(event, "Event"))}\n\n` `` (one JSON event per `data:` line, LF framing); `encodeBinary` gives protobuf only when the `accept` passed in prefers `application/vnd.ag-ui.event+proto`, else SSE bytes; `getContentType()` (`@ag-ui/encoder` `src/encoder.ts`). The docs page for `@ag-ui/encoder` is empty (https://docs.ag-ui.com/sdk/js/encoder.md); the README shows `encodeBinary` with content negotiation.
- This matches the HTTP+SSE binding (one event per `data`, LF line endings, https://docs.ag-ui.com/spec/1.0/basic/transports/http-sse). CopilotKit's runtime does exactly this: `new EventEncoder()` and `writer.write(encoder.encodeBinary(event))` into a `TransformStream` returned as `text/event-stream` (`handlers/shared/sse-response.ts` lines 74–76, 205–219, 289–296).
- Version declaration through a proxy: "Middlewares and proxies that pass a producer's `RUN_STARTED` through must leave its `protocolVersion` untouched … Only a layer that translates the stream into a different version declares the version it emits" (https://docs.ag-ui.com/migrating-to-1-0). Docs silent on whether running a 0.x stream through the client's compatibility boundary makes the proxy "a layer that translates" (**(opinion)**: it does; either leave `protocolVersion` absent as received or declare `"1.0"` because the hub emits 1.0-shaped events — pick one and record it).

## 2. CopilotKit's v2 runtime as the reference AG-UI backend-for-frontend

- **Run route** (`POST {base}/agent/:agentId/run`, docs `backend/runtime-endpoints.mdx` line 122): `handleRunAgent` clones the registered agent per request (`cloneAgentForRequest`), parses the browser's body with `RunAgentInputSchema` after a local legacy-null normalization (400 on failure; `handlers/shared/agent-utils.ts` lines 433–510), applies per-request **AG-UI middleware** with `agent.use(...)` (A2UI, MCP Apps, Open Generative UI; `agent-utils.ts` lines 83–163), merges headers (below), then `agent.setMessages(input.messages); agent.setState(input.state); agent.threadId = input.threadId` (`handlers/handle-run.ts` lines 33–78). Note: it passes the **browser's** messages through; it does not build the input on the server.
- **Re-encoding**: yes. The runner calls `agent.runAgent(input, { onEvent })` (so compat boundary, enforcement, chunk expansion and verification all run), pushes each event to ReplaySubjects, and `createSseEventResponse` re-encodes each with `EventEncoder` into a `TransformStream`, adds `: keep-alive` comments after 15 s of silence (`sse-keep-alive.ts` line 6), and answers `Content-Type: text/event-stream`, `Cache-Control: no-cache` (`sse-response.ts`).
- **Persistence**: in the runner. `InMemoryAgentRunner` keeps per thread the run's events, compacted with `compactEvents` at the end of each run, plus a messages snapshot (`runner/in-memory.ts` lines 755–777); `SqliteAgentRunner` persists to a file; custom runners override `run`/`connect` (docs `backend/agent-runner.mdx`).
- **The run is decoupled from the browser request**: "Start the agent execution immediately (not lazily)" (`in-memory.ts` line 879); when the browser disconnects, the SSE response only unsubscribes (`sse-response.ts` lines 280–282) and the agent run continues.
- **Connect** (`POST {base}/agent/:agentId/connect`, "resume streaming after a reconnect or page refresh", runtime-endpoints line 123): `connect()` replays all historic events of the thread compacted with `compactEvents`, then, if a run is active, bridges the live run's ReplaySubject, skipping messages already emitted (`in-memory.ts` lines 886–937).
- **Stop** (`POST {base}/agent/:agentId/stop/:threadId`, optional body `{ runId }`; any other key → 400, "because a stop cannot be undone", `handlers/handle-stop.ts` lines 15–38): `runtime.runner.stop({ threadId, runId? })` → `InMemoryAgentRunner.stop` marks `stopRequested`, then calls **`agent.abortRun()`** (for an `HttpAgent`: abort the upstream fetch) (`in-memory.ts` lines 944–990). The HTTP answer is JSON `{ stopped: true, interrupt: { type: "RUN_ERROR", message: "Run stopped by user", code: "STOPPED" } }` (`handle-stop.ts` lines 120–133). The run's own stream is then closed by `finalizeRunEvents`: if no terminal arrived, it closes open reasoning/text/tool calls/subagents and appends `RUN_FINISHED` with `outcome: { type: "cancelled" }` when the client declared `protocolVersion`, else a bare `RUN_FINISHED` (`packages/shared/src/finalize-events.ts` lines 204–227); if the upstream already produced a terminal (the `HttpAgent`'s synthesized `RUN_ERROR code "abort"`), nothing is appended (`finalize-events.test.ts` lines 108–134). Optional `onConcurrentRun: "supersede"` aborts a still-running run when a new one starts on the thread (`in-memory.ts` lines 609–647).
- **Headers to the agent**: by default the runtime forwards `authorization` and any `x-*` browser header minus a denylist; an explicit `forwardHeaders.allow` switches to allowlist mode; **server-configured `agent.headers` win on collision**, case-insensitively (`handlers/header-utils.ts` lines 162–288; docs `auth.mdx` line 116: "Headers the server configured on the agent itself still win on collision, so a service-to-service token can't be overridden from the browser").
- **Identity**: `identifyUser(request) → { id, name }` exists for the Intelligence runtime only and "is not an authentication gate"; "Reading a user id straight out of a header or request body hands every caller the ability to name themselves" (`auth.mdx` lines 500–576). For a self-hosted agent the docs forward the user's own `Authorization: Bearer <user token>` and have the agent validate it in a FastAPI dependency (`auth.mdx` lines 121–184). `properties` → `forwardedProps` "is not an auth channel" (line 116). Without Intelligence, thread ownership is "You do" (line 495).

## 3. Stop

### 3.1 The AG-UI spec

- Cancelled vs truncated (https://docs.ag-ui.com/spec/1.0/events/lifecycle#cancelled-runs): a **producer** that stops a run before completion for a non-failure reason MUST close it with `RUN_FINISHED` carrying the cancelled outcome, MUST close messages, tool calls, steps and subagents first, and "A producer that cannot close in order — the stop tore down the stream under it — reports `RUN_ERROR` instead". A cancelled run has no `result`, waits for nothing, and the next run "is an ordinary new run, not a resume". A consumer MUST NOT present it as success or as failure. "A consumer that abandons a stream — closes the connection, stops reading — has a truncated run, not a cancelled one: it MUST NOT synthesize a `RUN_FINISHED`".
- Truncation (https://docs.ag-ui.com/spec/1.0/basic/transports#truncation): no outcome; MUST NOT report it as success; "Whether and how to surface the truncation beyond that — leaving the run unresolved, or raising a synthetic failure — is the consumer's business; re-running is a new run with a new `runId`."
- **How a consumer asks a producer to stop: docs silent.** The 1.1 draft changelog lists "None yet" for every category (https://docs.ag-ui.com/spec/draft/changelog.md); the draft lifecycle and transport pages are identical to 1.0 apart from the draft banner (diffed). Open issues: #2417 (abortRun reports a stopped run like a completed one), #2327 (no cancel distinguishable from failure; a maintainer suggested `metadata: { finishedReason: "canceled" }` on `RUN_FINISHED`, before 1.0 added the outcome), #2871 (LangGraph: cancelling mid tool call leaves an unanswered `AIMessage.tool_calls` in the checkpoint; the next turn is rejected by OpenAI/Azure with 400).
- .NET hosting: the canonical endpoint passes the handler's `CancellationToken` to `GetStreamingResponseAsync` and `AsAGUIEventStreamAsync` (https://docs.ag-ui.com/sdk/dotnet/hosting/endpoints); in ASP.NET Core minimal APIs a `CancellationToken` parameter is "The cancellation token associated with the current HTTP request" (https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/parameter-binding, "Special types"), so a disconnect cancels the model call.

### 3.2 Pydantic AI 2.56.0's `AGUIAdapter` on a client disconnect

- Docs: "A client that disconnects (or aborts its request) is seen by the server as an external `asyncio.CancelledError` rather than a first-party cancellation …, so the bare `RUN_FINISHED` and `on_cancel` do not fire on a disconnect. To observe a stop gesture this way, keep the stream connected and cancel the run first-party via a `CancellationToken` triggered from a separate cancel endpoint" (`docs/ui/ag-ui.md` lines 46–47; same in `docs/ui/overview.md` line 30).
- Mechanism: Uvicorn 0.54.0 advertises ASGI `spec_version "2.3"` (`uvicorn/protocols/http/h11_impl.py` line 210, `httptools_impl.py` line 228) and answers `receive()` with `http.disconnect` once the connection is lost (`h11_impl.py` lines 115, 535–536). For spec < 2.4 Starlette 1.8.0's `StreamingResponse` runs `stream_response` and `listen_for_disconnect` in one task group and cancels the group when `http.disconnect` arrives (`starlette/responses.py` lines 245–283), so the body iterator (the adapter's event generator wrapping `agent.run_stream_events`) gets `CancelledError`, which cancels the in-flight model request. For servers advertising spec ≥ 2.4, Starlette instead relies on `send` raising `OSError` (`ClientDisconnect`) at the next write (lines 270–274).
- External cancellation semantics: the `CancelledError` "keeps propagating unchanged", with the run's history _attached_ for `RunCancelled.from_cancellation()` (`docs/agent.md` lines 787–789). With `dispatch_request` there is no hook that receives it (`on_cancel` is first-party only) — irrelevant for a stateless agent whose history the hub keeps.
- `on_complete(result: AgentRunResult)`: called when the run completes successfully, may yield extra events (`ui/_adapter.py` lines 561–573, docs). `on_cancel(cancelled: RunCancelled)`: only for first-party cancellation (`ctx.cancel()`, `AgentRun.cancel()`, a `CancellationToken`), "the place to persist `cancelled.all_messages()`" (`ui/_event_stream.py` lines 232–236, 336–368).
- On first-party cancellation the adapter closes open text/tool events, answers pending tool calls with an `'interrupted'` closeout, and emits a **bare `RUN_FINISHED`**: "AG-UI has no cancelled outcome; revisit when the protocol fills this spec gap" (`ui/ag_ui/_event_stream.py` lines 217–224; docs `ui/ag-ui.md` line 44). Under the 1.0 spec that reads as success (a 0.x gap; it only matters if the hub ever triggered first-party cancellation, which an AG-UI hub cannot do universally).
- Dangling tool calls in the next run's history: Pydantic AI repairs histories before each model request — it **adds** a synthesized `ToolReturnPart` with `outcome='interrupted'` and metadata `{'pydantic_ai_synthesized_tool_return': True}` for a call without a result, including a call whose arguments were cut off ("sent as `{"INVALID_JSON": "<raw args>"}`") (`docs/message-history.md` lines 255–268). The exception: "a new user prompt on top of a history whose final response still has unanswered tool calls … Pydantic AI raises" (`message-history.md` line 272; `_agent_graph.py` lines 745–752). Through the AG-UI adapter the new user message is the last `ModelRequest` and is replayed as the next request without a `user_prompt` (`_agent_graph.py` lines 686–700), so that raise is not reached; whether the mid-history repair covers the AG-UI case end to end is not stated in the docs (**(opinion)**: the spike should test it).
- AG-UI's own rule binds only **frontend** tool calls: "A thread that continues MUST answer every one of them first: the next run's `messages` carry a tool message per call … a failure is still an answer, as a tool message with `error` set … a history with a dangling call is one many models reject outright" (https://docs.ag-ui.com/spec/1.0/events/tool-calls#frontend-tools). For a **backend** tool call cut off by truncation the spec is silent; issue #2871 shows the failure mode (LangGraph + OpenAI 400).

### 3.3 How LibreChat and Open WebUI stop a generation

- **LibreChat**: a generation is a server-side job decoupled from the browser request; `GET /api/agents/chat/stream/:streamId` re-subscribes "with replay support" (`api/server/routes/agents/index.js` lines 183–190). Stop is `POST /api/agents/chat/abort` with `{ streamId | conversationId | abortKey, generationCreatedAt? }`, owner and tenant checked (403 otherwise; lines 591–702), then `GenerationJobManager.abortJob(...)`, which aborts the job's `AbortController` (also cross-replica through Redis pub/sub) and returns "all data needed for token spending and message saving" (`packages/api/src/stream/GenerationJobManager.ts` lines 4588–4601, 4864). The route **persists the partial turn** before publishing the final event, including an "empty unfinished assistant" (`index.js` lines 776–800).
- **Open WebUI**: a completion runs as an `asyncio` task registered per chat; `POST /api/tasks/chat/{chat_id}/stop` (verified user, chat ownership) calls `stop_task` → `task.cancel()` (local) or a Redis pub/sub "stop" command (`backend/open_webui/main.py` lines 2192–2215; `backend/open_webui/tasks.py` lines 259–290). The `CancelledError` handler closes the upstream body iterator "to … release the upstream connection" and **saves the partial output** with `done: True`, marking in-progress items and tool calls without output `'incomplete'`, and emits `chat:tasks:cancel` (`backend/open_webui/utils/middleware.py` lines 6639–6685).
- Both: the stop is a separate authenticated request, the upstream request is aborted (no protocol-level stop to the provider), the partial message is saved and marked, and generation continues when the browser merely disconnects.

## 4. Identity and auth from a trusted proxy to an agent

### 4.1 What AG-UI and the agent frameworks say

- AG-UI: "Authentication and authorization are properties of the binding and the application, not of the protocol: AG-UI defines no credential, and a binding carries whatever its channel uses (HTTP authentication, ambient process identity, or nothing)" (https://docs.ag-ui.com/spec/1.0/basic/transports). `HttpAgent` docs example: `headers: { Authorization: "Bearer your-api-key" }`. No end-user header is defined (docs silent). The middleware page's `AuthMiddleware` example writes a bearer into `forwardedProps` (https://docs.ag-ui.com/sdk/js/client/middleware lines 162–188), contradicting CopilotKit and Pydantic AI below.
- Microsoft Agent Framework (https://learn.microsoft.com/en-us/agent-framework/integrations/ag-ui/security-considerations, updated 2026-09-15): "AG-UI does not include a built-in authorization mechanism. Authenticate and authorize the exposed endpoint with your application framework"; thread ids are not proof of identity; "Scope storage by an authenticated user, tenant, workspace, or another application-owned boundary". No header convention for the end user (docs silent).
- Pydantic AI: `dispatch_request` takes `deps` "that you can vary for each request (e.g. based on the authenticated user)" (`docs/ui/ag-ui.md` line 41); "Validating [`forwardedProps`] proves shape, not identity: who the user is, what tenant they're in, and what they're allowed to do come from authenticated server state" (line 315); "UI adapter endpoints aren't authentication boundaries … Treat the adapter endpoint as an internal backend service" (`docs/ui/overview.md` line 162); authorize sensitive actions "inside the tool function itself — against the authenticated user carried in your dependencies" (line 178).
- AWS Strands' AG-UI app: an optional `auth` FastAPI dependency, example `if authorization != f"Bearer {os.environ['AGENT_TOKEN']}": raise HTTPException(401)`; "The ping endpoint stays unauthenticated so health probes keep working" (`integrations/aws-strands/python/src/ag_ui_strands/utils.py` lines 1105–1116).
- CopilotKit: §2 (server headers win; user token forwarded and validated by the agent; `properties`/`forwardedProps` not auth).

### 4.2 How hubs forward the end user

- **Open WebUI** `ENABLE_FORWARD_USER_INFO_HEADERS` (default `False`, `backend/open_webui/env.py` line 997): headers `X-OpenWebUI-User-Name`, `X-OpenWebUI-User-Id`, `X-OpenWebUI-User-Email`, `X-OpenWebUI-User-Role`, plus `X-OpenWebUI-Chat-Id`, `X-OpenWebUI-Message-Id` (tool servers only) and `X-OpenWebUI-Auth-Type` (`jwt` or `api_key`), each name configurable through `FORWARD_USER_INFO_HEADER_*` / `FORWARD_SESSION_INFO_HEADER_*` (env.py lines 999–1005). Docs: the four user headers go to "OpenAI, Ollama and Anthropic model connections, tool servers (OpenAPI and MCP)" and external RAG/audio/image services; "an OpenAI, Ollama or Pipelines request receives five of the six headers" (https://docs.openwebui.com/reference/env-configuration, "Security Variables"). Signed variant: with `FORWARD_USER_INFO_HEADER_JWT_SECRET` set, one HS256 JWT in `X-OpenWebUI-User-Jwt` (claims `sub`, `email`, `name`, `role`, `iss: "open-webui"`, `iat`, `exp`, default lifetime 300 s) replaces the four plain headers, "rather than relying on plaintext headers that anything on the network path could spoof" (env.py lines 1007–1016; `utils/headers.py` lines 41–85). Per-connection custom headers accept placeholders `{{USER_ID}}`, `{{USER_NAME}}`, `{{USER_EMAIL}}`, `{{USER_ROLE}}`, `{{USER_GROUPS}}`, `{{CHAT_ID}}`, `{{MESSAGE_ID}}`, … (`utils/headers.py` lines 115–155). **Pipes** are in-process Python functions and get the user as the `__user__` dict argument, not as headers (`backend/open_webui/functions.py` line 257).
- **LibreChat** custom endpoint `headers` (docs https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/custom_endpoint, "headers"): values support `${ENV_VAR}`, `{{LIBRECHAT_USER_*}}`, `{{LIBRECHAT_BODY_*}}` and `{{LIBRECHAT_OPENID_*}}`; the example is `X-User-ID: '{{LIBRECHAT_USER_ID}}'`, `X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'`. User placeholders: `ID, NAME, USERNAME, EMAIL, PROVIDER, ROLE, GOOGLEID, FACEBOOKID, OPENIDID, SAMLID, LDAPID, GITHUBID, DISCORDID, APPLEID, EMAILVERIFIED, TWOFACTORENABLED, TERMSACCEPTED, TERMSACCEPTEDAT` (`packages/api/src/utils/env.ts` lines 34–53); body placeholders `CONVERSATIONID`, `PARENTMESSAGEID`, `MESSAGEID` (line 151); plus `{{LIBRECHAT_OPENID_TOKEN|ACCESS_TOKEN|ID_TOKEN}}` and `{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}`. Unresolved recognized placeholders become empty strings; "A configured `Authorization` header takes precedence over the endpoint `apiKey` fallback" (docs).
- **Reverse-proxy convention**: oauth2-proxy passes `X-Forwarded-User`, `X-Forwarded-Email`, `X-Forwarded-Groups`, `X-Forwarded-Preferred-Username` upstream (`--pass-user-headers`, default true) and `X-Auth-Request-User|Email|Groups|Preferred-Username` in nginx `auth_request` mode (https://github.com/oauth2-proxy/oauth2-proxy/blob/master/docs/docs/configuration/overview.md lines 143–151; v7.15.5).

### 4.3 Standards

- **No standard header for an end-user id.** RFC 7239 `Forwarded` carries hop data (`by`, `for`, `host`, `proto`: network addresses and the original host/scheme, https://www.rfc-editor.org/rfc/rfc7239 §5), not an authenticated user. RFC 6648 says new parameter names "SHOULD NOT" use an `X-` prefix (https://www.rfc-editor.org/rfc/rfc6648 §3); the hubs above use `X-` anyway.
- **IETF Transaction Tokens** (draft-ietf-oauth-transaction-tokens-11, 2026-07-30, Standards Track, state "WG Consensus: Waiting for Write-Up", https://datatracker.ietf.org/doc/draft-ietf-oauth-transaction-tokens/): signed short-lived JWTs that "propagate user identity, workload identity and authorization context throughout the Call Chain within a trusted domain", sent in a dedicated `Txn-Token` HTTP header; "the standard HTTP Authorization header MUST NOT be used because that may be used by the workloads for other purposes" (§12, §12.1). It assumes a Transaction Token Service; a draft, not yet an RFC.
- **OpenAI's body fields**: Chat Completions `user` is "Deprecated. This field is being replaced by `safety_identifier` and `prompt_cache_key`"; `safety_identifier` is "A stable identifier … max 64 characters. We recommend hashing their username or email address" (https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create, via Context7). Model-API specific; AG-UI has no such field, and `forwardedProps` is "passed through to the agent untouched" application data (run-input page), which CopilotKit and Pydantic AI say is not an auth channel.

### 4.4 Convention options, summarised

| Option | Who does it | Strength | Source |
| --- | --- | --- | --- |
| Service token: `Authorization: Bearer <per-agent secret>` set on the server | AG-UI `HttpAgent` docs, CopilotKit (server headers win), Strands `auth` example | Authenticates the hub, not the user | §4.1 |
| Plain identity headers (`X-…-User-Id`, name, email, role) | Open WebUI default, LibreChat templates, oauth2-proxy | Trust rests on the network and the service token; spoofable by anything else on the path | §4.2 |
| Signed identity header (short-lived HS256 JWT, `sub` = user id) | Open WebUI `X-OpenWebUI-User-Jwt`; IETF `Txn-Token` (draft) | Verifiable by the agent; needs a shared key per agent | §4.2, §4.3 |
| Forward the user's own bearer token; agent validates it | CopilotKit self-hosted examples | Needs a user token the agent can verify (OIDC); the hub uses session cookies | §2 |
| Identity in the body (`forwardedProps`, OpenAI `user`) | AG-UI middleware example only | Advised against by CopilotKit and Pydantic AI | §4.1 |

## 5. Test connection for an AG-UI agent

- **No discovery in the protocol**: "No transport binding in this version carries a capabilities exchange" (https://docs.ag-ui.com/spec/1.0/basic/capabilities#retrieval); the only AG-UI method is `POST` with a `RunAgentInput` (http-sse page). No health endpoint is defined (docs silent).
- What references expose (each framework-specific):
  - AG-UI LangGraph FastAPI helper: `GET {path}/health` → `{"status": "ok", "agent": {"name": …}}` (`integrations/langgraph/python/ag_ui_langgraph/endpoint.py` lines 52–59); watsonx the same (`ag_ui_watsonx/endpoint.py` line 55).
  - AWS Strands app: `GET /ping` → `{"status": "healthy"}`, unauthenticated by design (`ag_ui_strands/endpoint.py` lines 444–456; `utils.py` lines 1073, 1172).
  - LangSmith Deployment / Agent Server (not AG-UI): `GET /ok` health check and `GET /info` (https://docs.langchain.com/langsmith/agent-server-api/system/health-check).
  - CopilotKit runtime (not AG-UI): `GET {base}/info` lists registered agents; "The fastest way to confirm a self-hosted runtime is wired up is to hit `/info`" (runtime-endpoints.mdx lines 120, 290).
  - Pydantic AI: no health route; the docs mount `Starlette(routes=[Route('/', run_agent, methods=['POST'])])` (`docs/ui/ag-ui.md` lines 160, 243, …), so a `GET` gets Starlette's 405 for a path that matches with another method — framework behaviour, not AG-UI. `OPTIONS` depends on whether CORS middleware is installed (docs silent).
- **What an AG-UI endpoint returns for a malformed body**: the spec requires a plain HTTP error before any stream — "a structurally invalid `RunAgentInput` is refused before `RUN_STARTED`, outside the stream" (transports, binding contract) and "Input rejected before the run starts — malformed JSON, failed validation, refused auth — is an HTTP error status with no event stream" (http-sse, Errors). The spec does not fix the status code (docs silent). Observed implementations:
  - Pydantic AI `dispatch_request`: `415` when `Content-Type` is not `application/json` (checked before the body is read, a CSRF guard); `422` with the Pydantic error JSON when validation fails (`ui/_adapter.py` lines 104–152, 884–887).
  - FastAPI-based helpers (LangGraph `input_data: RunAgentInput` body param; Strands `RequestValidationError`): `422`; Strands `415` for a non-JSON media type, `400` for an unreadable body (`ag_ui_strands/endpoint.py` lines 40–85).
  - ASP.NET Core minimal API (`[FromBody] RunAgentInput`, the .NET hosting pattern): `400` "Failure to deserialize JSON body", `415` "Wrong content type" (https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/parameter-binding, "Binding failures").
  - CopilotKit runtime: `400` (`agent-utils.ts` lines 456–510).
- **Order of auth vs validation** (FastAPI 0.143.0): the body is read and JSON-decoded **before** dependencies are solved, so malformed JSON → `422 json_invalid` even without a valid token (`fastapi/routing.py` lines 446–499); for well-formed JSON, sub-dependencies (an auth dependency) are solved **before** body validation (`fastapi/dependencies/utils.py` lines 619 vs 702), so a refused token → 401/403 first. Pydantic AI's `dispatch_request` runs inside the user's route, after any auth dependency or middleware. Strands runs route dependencies before `_parse_run_agent_input` (comment "after route dependencies run", `endpoint.py` line 57).
- Is "POST an invalid `RunAgentInput`, expect 4xx" documented anywhere as a reachability check? **No (docs silent)**; it is derived from the spec's error rule above.

## 6. Next.js 16.3.4 Route Handler streaming

- Docs, `01-app/02-guides/streaming.md` "Streaming in Route Handlers" (lines 482–570): Route Handlers "can stream raw responses using the Web Streams API … useful for Server-Sent Events"; example `new Response(new ReadableStream({ start(controller) { … } }))`.
- Same guide "What can affect streaming" (lines 687–730): reverse proxies (nginx) buffer by default → `X-Accel-Buffering: no`; CDNs; serverless (AWS Lambda needs streaming mode); compression "can buffer chunks"; Safari buffers the first 1024 bytes. Platform support: Node.js server and Docker yes (lines 783–790).
- Compression: Next gzips by default under `next start` (`03-api-reference/05-config/01-next-config-js/compress.md`). Source: the router server installs the `compression` middleware (`dist/server/lib/router-server.js` lines 257–265) and Next's pipe calls `res.flush()` after every chunk ("Added by the `compression` middleware, this is a function that will flush the partially-compressed response to the client", `dist/server/pipe-readable.js` lines 80–85), so gzip does not hold SSE chunks (docs silent; source only).
- `02-guides/backend-for-frontend.md` "Proxying to a backend" (lines 443–500): validate, then `return fetch(proxyRequest)`. "Deployment environment" (lines 920–926): hosts that deploy Route Handlers as lambdas may terminate long-running handlers; self-hosted Node has no such limit stated.
- `request.signal` on client disconnect: **docs silent** for Node-runtime Route Handlers (only the adapters page lists `signal?: AbortSignal` for edge entrypoints). Source: `NextRequestAdapter` creates an `AbortController` that aborts with `ResponseAborted` when the response emits `close` before `writableFinished` ("If `close` fires first, then we know the client disconnected before we finished", `dist/server/web/spec-extension/adapters/next-request.js` lines 45–63).
- Upstream fetch timeouts: Node's `fetch` is undici; `headersTimeout` and `bodyTimeout` default to 300 s, `bodyTimeout` "Monitors the time between consecutive body chunks" (undici `docs/api/Client.md`, `getting-started.md` "Timeouts", via Context7). An agent silent for more than 5 minutes (a long tool call without keep-alives) fails the hub's fetch with `BodyTimeoutError`. Pydantic AI's `streaming_response` sends no keep-alive comments (no match in `ui/`); CopilotKit's runtime sends `: keep-alive` after 15 s; the AG-UI binding says consumers "MUST tolerate SSE comment lines (`: keep-alive`), which producers MAY send at any cadence" (http-sse).
- What the hub's Dify proxy already does (`lib/providers/dify/client.ts`): `passthrough()` returns `new Response(upstream.body, …)` with the upstream status and a kept-headers list, plus `Cache-Control: no-store` and `X-Accel-Buffering: no` (lines 81–95); streaming calls take `request.signal` so "The client's abort (a stopped reply) cancels the upstream fetch" (`app/api/dify/[appId]/chat-messages/route.ts` line 19); Dify's own stop is a separate route (`…/chat-messages/[taskId]/stop`); network failures become `502 upstream_unreachable` with the cause logged server-side only (client.ts lines 158–174); Test connection uses `AbortSignal.timeout(10_000)` and maps 401 → `key_refused`, network/5xx → `unreachable`, anything else → `upstream_error` (`lib/providers/dify/test-connection.ts`).

## Implications for the hub (opinion)

### A. The server-side client

1. **Use `@ag-ui/client`'s `HttpAgent.runAgent()` on the server with a subscriber's `onEvent`**, one new `HttpAgent` per run (it holds per-run state: `messages`, `state`, `abortController`, `pendingInterrupts`), constructed with `url`, the server-side `headers`, `threadId`, `initialMessages` and `initialState` from the hub store, and called with `{ runId, tools, context, forwardedProps, resume, abortController }`. This is the only path the AG-UI docs describe that applies the always-on 0.x → 1.0 boundary, enforcement, chunk expansion and verification, and it is how CopilotKit's runtime does it. Do not consume `HttpAgent.run()` directly (raw, untranslated events). The hand-built pipeline from exported pieces (§1.2 (b)) works per the typings but is undocumented; keep it as a fallback only.
2. **Re-encode with `EventEncoder.encodeSSE`** into a `ReadableStream`/`TransformStream` returned from the Route Handler with `Content-Type: text/event-stream`, `Cache-Control: no-store`, `X-Accel-Buffering: no` (the Dify passthrough's headers), plus `: keep-alive` comments every ~15 s of silence (CopilotKit's default, spec-tolerated).
3. **Persist from the same subscriber as events arrive** (charter §4.2: "written as a run streams"): keep the event log (compact at run end with `compactEvents`, as CopilotKit does) and derive messages from `agent.messages`/`onMessagesChanged`, not only from `newMessages` (which misses messages updated under existing ids). Keep `onEvent` writes cheap or batched: it is awaited per event.
4. **Treat the runAgent outcome carefully**: `runAgent()` resolves on an abort and on a `RUN_ERROR`; read the terminal event in the subscriber (`onRunFinishedEvent` with `outcome`, `onRunErrorEvent`) and track "no terminal received" yourself. Watch #2417: a later 1.0.x may make `runAgent()` reject on truncation.
5. **Set the upstream fetch timeouts deliberately**: pass `HttpAgent`'s `fetch` option a fetch bound to an undici `Agent` whose `bodyTimeout` fits the longest expected silent tool call (or use the hub's own idle timer), since Pydantic AI sends no keep-alives and undici's default is 300 s between chunks.
6. **Accept the dependency cost knowingly**: client and encoder bring `rxjs` and a second zod (3.25.x, via the client and `@ag-ui/proto`). Use `@ag-ui/core` (zod-free main entry, zod 4 peer for `/schemas`) for the hub's own types and validation of browser input. This is an ADR-worthy dependency decision (ADR-0015).

### B. Stop semantics

1. **Give the hub its own stop route** (like CopilotKit's `stop/:threadId` with an optional `runId`, LibreChat's `/chat/abort`, Open WebUI's `/api/tasks/chat/{id}/stop`), e.g. `POST /api/apps/[appId]/threads/[threadId]/runs/[runId]/stop`, guarded like every provider route and scoped to the run's owner. It aborts the upstream request through the run's `AbortController` (the only universal lever: AG-UI has no stop request), which a Starlette/FastAPI agent sees as a disconnect → `CancelledError` → its model call is cancelled; ASP.NET agents see their request `CancellationToken` fire.
2. **As the producer toward the browser, close the run as cancelled**: close every message/tool call/reasoning/step still open and emit `RUN_FINISHED { outcome: { type: "cancelled" } }` (what CopilotKit's `finalizeRunEvents` does), and drop the `HttpAgent`'s synthesized `RUN_ERROR { code: "abort" }` for a stop the hub itself requested. The hub can close in order because it tracks what is open, so the spec's "cannot close in order → RUN_ERROR" clause does not apply to it. Store the run as cancelled; never as success or failure.
3. **Browser disconnect without a stop**: two documented patterns exist. (a) Abort upstream (today's Dify route; simplest; the stored run is _truncated_, shown as stopped). (b) Keep the upstream run going and let the browser re-attach from the store (CopilotKit `connect`, LibreChat resumable streams, Open WebUI tasks). Recommend (a) for Part 2 with the store written as events arrive, and keep (b) as a later option; record the choice in the Part 2 ADR. With several hub containers later, a stop must reach the container holding the run (LibreChat and Open WebUI use Redis pub/sub); for one container, an in-process map `runId → AbortController` is enough.
4. **Next run after a stop**: for every tool call the stopped run left without a result, the hub appends a `tool` message with `error` set (e.g. "Interrupted: the user stopped the run") when it builds the next `RunAgentInput`. The spec requires this for frontend tools and is silent for backend ones; doing it for both mirrors Pydantic AI's synthesized `'interrupted'` returns and Open WebUI's `'incomplete'` marking, and avoids the LangGraph/OpenAI 400 of issue #2871. Truncated argument JSON stays as received (the spec leaves unparsable arguments to the application). The spike should verify Pydantic AI accepts this history shape.

### C. Identity and auth header convention

1. **Service auth**: a per-app `Authorization: Bearer <secret>` from the app's `secrets` jsonb, set only on the server (CopilotKit's precedence rule: the browser can never set or override it). The hub forwards no browser header to the agent.
2. **End user**: send ADR-0026's permanent account id only, in a dedicated header, since no standard header exists. Recommended shape: a short-lived signed JWT (HS256 with a per-app shared key; `sub` = account id, `aud` = the app id, `iss` = the hub, `exp` ≈ 5 min), modelled on Open WebUI's `X-OpenWebUI-User-Jwt` and in the spirit of the IETF `Txn-Token` draft, so the agent can verify identity instead of trusting the network. If the owner prefers simplicity for agents on the same Docker network, a plain `…-User-Id` header next to the bearer is the Open WebUI/LibreChat default, with the trust argument written down. Make the header names configurable per app (Open WebUI, LibreChat). Name choice per RFC 6648: no `X-` prefix for a new name (e.g. `AI-App-Hub-User`); **(opinion)** either way, the name is recorded in the AG-UI provider ADR and documented for agent authors (Pydantic AI: read it in the route and put it in `deps`).
3. **Never send email or name by default**: AGENTS.md forbids sending the owner's email to any other service, and the permanent id is enough for `deps`. Never use `forwardedProps` or `context` for identity.

### D. Test connection

1. **Spec-based probe**: `POST <agent URL>` with the configured bearer, `Content-Type: application/json`, `Accept: text/event-stream`, body `{}` (valid JSON, structurally invalid `RunAgentInput`: no `threadId`/`runId`/`messages`), `AbortSignal.timeout(10_000)` like the Dify test. A conforming producer must refuse it with an HTTP error before any stream, so no run starts and no model is called. Map the answer: `400`/`422` → reachable (and, for agents whose auth runs before validation, credential accepted); `401`/`403` → `key_refused`; `404`/`405` → wrong URL (`upstream_error`); `415` → upstream error (should not happen with JSON); `5xx`, network errors or the timeout → `unreachable`; `2xx` with `text/event-stream` → the producer started a run on invalid input: abort at once and report a non-conformance warning. Read at most a small error body and never echo it.
2. **Caveat**: `422` proves only reachability where the agent validates before it authenticates; well-formed JSON keeps FastAPI auth dependencies ahead of body validation, which is why the probe body is `{}` and not broken JSON (malformed JSON would get a `422` before auth runs in FastAPI).
3. **Rejected alternatives**: `GET`/`HEAD`/`OPTIONS` and framework health routes (`/health`, `/ping`, `/ok`, `/info`) are not AG-UI and differ per framework (an optional "health URL" field could be added later); a minimal real run costs a model call and writes agent-side state.
4. **Label it in the ADR as the hub's own convention derived from the spec's error rule**, since no AG-UI document describes a reachability check.
