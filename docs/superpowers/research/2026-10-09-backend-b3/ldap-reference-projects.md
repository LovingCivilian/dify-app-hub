# LDAP account lifecycle in reference projects (B3 research)

Date: 2026-10-09. Scope: how eight well-known projects link, create, refresh, collide, deactivate, re-check and map LDAP accounts, with sources pinned to a commit. Purpose: give the B3 design the citations ADR-0002 asks for where the docs leave the design open.

Projects: LibreChat, Open WebUI and Rocket.Chat (the required three, same stack or same category), then GitLab, Mattermost, Grafana, Keycloak user federation and Nextcloud `user_ldap`, plus next-auth v4's documented position on linking accounts by email.

Method: Context7 for the docs index (LibreChat, Open WebUI, Rocket.Chat, NextAuth.js). Each project's docs repository and source read at the pinned commits listed at the end. Shallow sparse clones live in `tmp/b3-research/src/ldap-*`, and no code from them was run. Citations use `repo@short-sha:path:line`. Docs excerpts saved beside this file have a `.txt` suffix (`owui-*.txt`, `rc-*.txt`, `mm-*.txt`, `nc-*.txt`, `kc-*.txt`, `grafana-enhanced-ldap.md.txt`, `nextauth-*.txt`).

Short SHAs used below (the full SHAs are in "Pinned sources"): `LC`=danny-avila/LibreChat@e1dfc104, `LCD`=LibreChat-AI/docs@9fdcbff6, `OW`=open-webui/open-webui@8bd8b4fa, `OWD`=open-webui/docs@81b07ae4, `RC`=RocketChat/Rocket.Chat@a6ae1988, `RCD`=RocketChat/docs@22db3da5, `GL`=gitlabhq/gitlabhq@0739b8bf, `MM`=mattermost/mattermost@4d94455a, `MMD`=mattermost/docs@bd09d959, `GF`=grafana/grafana@7b702d79, `KC`=keycloak/keycloak@c7de391a, `NC`=nextcloud/server@859e88ab, `NCD`=nextcloud/documentation@ea18f453, `NA4`=nextauthjs/next-auth (branch v4)@d857eec5, `NAD`=nextauthjs/docs@938c7030.

## 1. LibreChat (Node/Express + Passport, AI chat hub)

1. **Identity key.** `ldapId` = the attribute named by `LDAP_ID`, else `uid`, else `sAMAccountName`, else `mail`: `(LDAP_ID && userinfo[LDAP_ID]) || userinfo.uid || userinfo.sAMAccountName || userinfo.mail` (`LC:api/strategies/ldapStrategy.js:102-103`). The docs say "Specify a unique user ID. By default, uid or sAMAccountName, mail is used." (`LCD:content/docs/configuration/authentication/ldap.mdx:40`). They do not mention objectGUID or entryUUID. The key is stored as a field on the user document (`ldapId`, `LC:packages/data-schemas/src/schema/user.ts:88`) next to `provider: 'ldap'`. Each external provider has its own id field (`googleId`, `openidId`, `samlId`, `ldapId`, …), and each field has a partial unique index per tenant (`user.ts:243-266`). There is no separate identities table.
2. **Login flow.** It uses `passport-ldapauth` (ldapauth-fork): the server binds with `LDAP_BIND_DN`, searches with `LDAP_SEARCH_FILTER` (default `mail={{username}}`, `ldapStrategy.js:75`), then binds as the found entry ("verify the given password by trying to bind the user client with the found LDAP user object", `vesse/node-ldapauth-fork@5f8b7b16:README.md:80-85`). There is one form, and LDAP replaces local login. When `LDAP_URL` and `LDAP_USER_SEARCH_BASE` are set, `POST /login` uses `requireLdapAuth` _instead of_ `requireLocalAuth` (`LC:api/server/routes/auth.js:67,77`). `LDAP_LOGIN_USES_USERNAME` only switches the form to a username field (`LC:api/server/services/Config/ldap.js:10-17`). The account is found by `ldapId` only (`LC:packages/api/src/auth/ldap.ts:23`). If that account belongs to another provider, the login fails with `AUTH_FAILED` (`ldap.ts:24-27`).
3. **JIT creation.** The account is created at the first login with `{ provider: 'ldap', ldapId, username, email, emailVerified: true, name, role }`. The role is ADMIN for the first account in the deployment and USER otherwise (`ldap.ts:67-70`). When the entry has no email, the email falls back to `username + '@ldap.local'` with a warning (`ldapStrategy.js:114-126`). The directory values are refreshed at every login: "LDAP manages these users' identity, so provider, `ldapId`, email, username and name are overwritten on every login" (`ldap.ts:31-35,85-89`).
4. **Same-email collision.** LibreChat does not link. Email is unique per tenant (`user.ts:233`). A first LDAP login whose email belongs to a local account gets `user_exists` on insert. The lookup by `ldapId` then finds nothing, and `createUserOnce` throws "New user conflicts with an account the lookup cannot resolve" (`LC:packages/api/src/auth/provision.ts:85-96`), so the login fails. There is no setting for this. The test "blocks login if an existing user has a different provider" covers the same-`ldapId` case (`LC:api/strategies/ldapStrategy.spec.js:112-128`).
5. **Removal or disable.** LibreChat does not handle it. There is no sync job and no re-check of the directory. A removed entry only stops future LDAP logins, and tokens already issued last until they expire. No LDAP sync or deactivation code exists under `api/` or `packages/api/src`.
6. **Role mapping.** Roles are set locally only. The first user becomes ADMIN, and later logins never write the role (`role` is not among the refreshed `directoryValues`, `ldap.ts:85`). OpenID has role sync (`packages/api/src/auth/openidRoleSync.ts`), but LDAP does not.
7. **Group sync.** None for LDAP.
8. **Configuration.** Environment variables only: `LDAP_URL` (`ldap://` or `ldaps://`), `LDAP_BIND_DN`, `LDAP_BIND_CREDENTIALS`, `LDAP_USER_SEARCH_BASE`, `LDAP_SEARCH_FILTER`, `LDAP_CA_CERT_PATH`, `LDAP_TLS_REJECT_UNAUTHORIZED`, `LDAP_STARTTLS`, `LDAP_LOGIN_USES_USERNAME`, `LDAP_ID`, `LDAP_USERNAME`, `LDAP_EMAIL`, `LDAP_FULL_NAME` (`LC:.env.example:1158-1171`; `LCD:…/ldap.mdx:13-119`).

## 2. Open WebUI (Python/FastAPI, AI chat hub)

1. **Identity key.** The email. Open WebUI stores no directory id and finds the account with `Users.get_user_by_email(email)` (`OW:backend/open_webui/routers/auths.py:647`). The users table has `oauth` and `scim` JSON columns for other providers, but nothing for LDAP (`OW:backend/open_webui/models/users.py:170-171`). This is not configurable.
2. **Login flow.** It is search-then-bind. The server binds with `LDAP_APP_DN`/`LDAP_APP_PASSWORD`, or anonymously when no DN is set (`auths.py:534-542`). It then searches `(&(<LDAP_ATTRIBUTE_FOR_USERNAME>=<typed, escaped>)<LDAP_SEARCH_FILTER>)` (`auths.py:561`), checks that the typed name is one of the entry's username values (`:636`), and binds as the entry's DN (`:637-643`). Empty passwords are refused before the bind, citing RFC 4513 §5.1.2 (`:492-498`). The login attribute defaults to `uid` (`OW:backend/open_webui/config.py:2798`). LDAP is a separate mode on the sign-in page. It is the default mode when enabled, and a "Continue with LDAP" / "Continue with Email" toggle appears when the email form is also enabled (`OW:src/routes/auth/+page.svelte:34,589-604`). If both a local account and an LDAP entry match, the LDAP mode signs into the local account that has the same email.
3. **JIT creation.** The account is created with the email, a random password `str(uuid.uuid4())`, `name` = `cn`, and `role` = `ui.default_user_role`. The first account becomes admin (`auths.py:647-667`). The docs say: "a new user account is created automatically in Open WebUI with the instance's default role, which is `pending` unless an administrator changed it" (`OWD:docs/features/authentication-access/auth/ldap.mdx:157`). The email is required: the login fails with "User does not have a valid email address." (`auths.py:579`). Name and email are not refreshed on later logins, because the handler has no update path.
4. **Same-email collision.** Open WebUI links automatically by email, with no setting. Its own OAuth path does the opposite: `OAUTH_MERGE_ACCOUNTS_BY_EMAIL` defaults to False and is documented as "considered unsafe as not all OAuth providers will verify email addresses and can lead to potential account takeovers" (`OWD:docs/reference/env-configuration.mdx:6309-6315`).
5. **Removal or disable.** LDAP removal is not handled, and there is no sync. Login refuses inactive accounts through `Auth.active` (`OW:backend/open_webui/models/auths.py:34,188`). Deactivation comes from an admin or from SCIM 2.0: `ENABLE_SCIM` "Enables the SCIM 2.0 endpoints … so an identity provider can create, update and deactivate users and groups" (`OWD:…/env-configuration.mdx:7066-7069`).
6. **Role mapping.** No LDAP role mapping exists. OAuth has `ENABLE_OAUTH_ROLE_MANAGEMENT`, but the `ldap.*` keys have no role keys (`config.py:3211-3227`). An administrator changes roles locally (`OWD:…/ldap.mdx:157`).
7. **Group sync.** `ENABLE_LDAP_GROUP_MANAGEMENT` reads `LDAP_ATTRIBUTE_FOR_GROUPS` (default `memberOf`) and keeps the first CN of each group DN (`auths.py:591-631`). `ENABLE_LDAP_GROUP_CREATION` creates missing groups by name (`OW:backend/open_webui/models/groups.py:480-514`). `sync_groups_by_group_names` then sets the user's membership to exactly that list. It removes the user from every other group, including ones made locally in the hub (`groups.py:516-572`). This runs at each LDAP login, and only when the list is non-empty (`auths.py:693-697`). Groups are matched by name, with no external id. There is no nested-group handling beyond what `memberOf` returns.
8. **Configuration.** Environment variables seed the settings, and then the admin panel owns them: "Open WebUI reads these environment variables only on the first startup. Subsequent changes must be made in the Admin settings panel … unless you have `ENABLE_PERSISTENT_CONFIG=false`" (`OWD:…/ldap.mdx:109`). TLS: `LDAP_USE_TLS` (default True) is passed as `use_ssl`, which means LDAPS (`auths.py:531`). Also `LDAP_CA_CERT_FILE`, `LDAP_VALIDATE_CERT` and `LDAP_CIPHERS` (`config.py:2785-2820`). The code has no StartTLS.

## 3. Rocket.Chat (Node/Meteor, chat)

Licensing: from 9.0.0, LDAP login needs a Premium plan ("LDAP authentication will require a Premium plan starting on version 9.0.0", `RC:apps/meteor/server/lib/premiumAuthDeprecation.ts`). Background sync, active-state sync and role, channel and team sync are already premium (`apps/meteor/ee/`).

1. **Identity key.** Configurable through `LDAP_Unique_Identifier_Field`. The default is `objectGUID,ibm-entryUUID,GUID,dominoUNID,nsuniqueId,uidNumber,uid` (`RC:apps/meteor/server/settings/ldap.ts:145`). The docs say "The field that links the LDAP user and the Rocket.Chat user … The default value is `objectGUID,ibm-entryUUID,GUID,dominoUNID,nsuniqueId,uidNumber`" (`RCD:use-rocket.chat/authentication/ldap/ldap-data-sync-settings.md`). If none of those attributes is present, the user search field is used, then the DN (`RC:apps/meteor/server/lib/ldap/Manager.ts:403-435`). The value is stored as the hex of the raw bytes (`ldapUser._raw[key].toString('hex')`, `:428-431`), so binary objectGUID works. It is stored on the user document as `services.ldap: { id, idAttribute }` plus `ldap: true` (`Manager.ts:203-208`). Note: OpenLDAP's `entryUUID` is **not** in the default list (only IBM's `ibm-entryUUID` is). On OpenLDAP the default therefore falls to `uidNumber` or `uid` unless the admin adds `entryUUID`.
2. **Login flow.** It is search-then-bind with a service account (`LDAP_Authentication_UserDN`/`Password`, `settings/ldap.ts:28-44`). The search uses `LDAP_User_Search_Field` (default `uid`, `sAMAccountName` on AD, comma lists allowed: "You can use multiple values separated by a comma to allow users to log in using multiple identifiers like username or email", `RCD:…/ldap-user-search.md:35`). It needs exactly one result and passes the optional group filter, then binds as the DN (`Manager.ts:228-259`). There is one form. If LDAP finds no user, the login falls through to the local password handler (`Manager.ts:44-46,535-555`). Local password logins by LDAP-linked users are blocked unless Login Fallback is on: "LDAP users can still login locally when login fallback is enabled" (`RC:apps/meteor/server/configuration/ldap.ts:20-53`). Login Fallback (default false, `settings/ldap.ts:26`) also stores the LDAP password as the local password at each LDAP login (`Manager.ts:338-340`), described as "Helps when the LDAP is down for some reason" (en i18n `LDAP_Login_Fallback_Description`).
3. **JIT creation.** The account is created through the importer's converter with: username (`LDAP_Username_Field`, templates like `#{givenName}.#{sn}`), emails, name (`cn`), avatar, and `importIds: [dn]` (`Manager.ts:183-222`). The email comes from `LDAP_Email_Field`, else `username@<LDAP_Default_Domain>`, else `mail`. Otherwise the login fails with "Failed to get email address from LDAP user" (`Manager.ts:451-475`). Update User Data on Login is on by default (`settings/ldap.ts:155`).
4. **Same-email collision.** It is governed by **Merge Existing Users**, default false (`settings/ldap.ts:150`). With merge off, an unlinked local user with the same username causes "LDAP Authentication succeeded, but there's already an existing user with provided username [x] in Mongo." (`Manager.ts:352-357`). With merge off, the converter does not look for an existing user by email (`RC:apps/meteor/server/lib/ldap/UserConverter.ts:33-35`). With merge on, it matches an unlinked local user by email first, then by username (`UserConverter.ts:37-47`). The setting's own warning reads: "_Caution!_ When importing a user from LDAP and an user with same username already exists the LDAP info and password will be set into the existing user." Background sync has its own `LDAP_Background_Sync_Merge_Existent_Users` (default false).
5. **Removal or disable (premium).** Background Sync is off by default, with an interval of `every_24_hours` (choices 1/6/12/24/48 h, `RC:apps/meteor/ee/server/settings/ldap.ts:22-58`). It runs as a cron job in the server process (`RC:apps/meteor/ee/server/configuration/ldap.ts`, `cronJobs.add`). "Automatically disable users that are no longer found on LDAP" (`Disable_Missing_Users`, default false) deactivates the users who were not found (`RC:apps/meteor/ee/server/lib/ldap/Manager.ts:730-748`). Deactivating unsets the login tokens, which ends the sessions (`RC:apps/meteor/server/lib/users/setUserActiveStatus.ts:122-123`). "Sync User Active State" (default `disable`, `ee/server/settings/ldap.ts:98-108`) reads `loginDisabled`, `orclIsEnabled`, and AD `userAccountControl` bit 2 (`ee/server/lib/ldap/Manager.ts:639-659`), at login and at sync. Reactivation happens only with `enable` or `both` (`copyActiveState`, `:661-686`). Under the default, a user disabled as "missing" stays disabled. Auto Logout is off by default (`*/5 * * * *`): it unsets the tokens of users who are disabled in LDAP (`:811-825`). Docs: "Any rooms owned by those users will be automatically assigned to new owners" (`RCD:…/ldap-premium-settings.md`).
6. **Role mapping (premium).** "Sync LDAP Groups" (default off) uses a JSON map from group to role(s), for example `{"rocket-admin": "admin"}`. "Auto Remove User Roles" (default off) "will only remove roles automatically that are set under the User Data Group Map" (`RCD:…/ldap-premium-settings.md`; `ee/server/lib/ldap/Manager.ts:326-402`). It runs at each login (`onLDAPLogin` → `advancedSyncForUser`, `ee/server/configuration/ldap.ts`) and at background sync.
7. **Group sync (premium).** LDAP groups map to channels and teams (JSON maps), at login and at sync, with optional auto-removal. "Validate mapping for each login" is optional for teams. There is no general group entity and no nested-group setting. A group filter can limit who may log in (`LDAP_Group_Filter_*`).
8. **Configuration.** Admin UI settings: Host, Port, Reconnect, Login Fallback, Authentication (User DN/Password), Encryption (`plain` / `tls` = StartTLS / `ssl` = LDAPS), CA Cert, Reject Unauthorized, timeouts, Base DN, User Search Filter, Scope, Search Field, page and size limits (`RC:apps/meteor/server/settings/ldap.ts:10-120`).

## 4. GitLab (Ruby on Rails)

1. **Identity key.** The **DN**, stored in a separate `identities` table (`provider` such as `ldapmain`, `extern_uid` = the normalized DN, `user_id`) (`GL:db/structure.sql:22572-22583`; `GL:app/models/identity.rb:9-13,35-41`). The docs say: "When an LDAP server creates a user in GitLab, the user's LDAP DN is linked to their GitLab account as an identifier." (`GL:doc/administration/auth/ldap/_index.md:1418-1419`). The fallback is the email: `find_by_uid_and_provider || find_by_email || build_new_user` (`GL:lib/gitlab/auth/ldap/user.rb:16-18`). A GUID cannot be used as the key.
2. **Login flow.** A `bind_dn` search on `uid` plus `user_filter`, then a bind as the DN (`GL:lib/gitlab/auth/ldap/authentication.rb:28-36,47-68` for Git over HTTP; omniauth-ldap for the web). `uid` is the login attribute (`sAMAccountName`, `uid` or `userPrincipalName`). `allow_username_or_email_login` strips everything after the first `@` (`_index.md:308,317`). The sign-in page has a separate **LDAP tab**. Disabling LDAP web sign-in means "users don't see an **LDAP** tab on the sign-in page" (`_index.md:1162`). Once linked, "they can no longer use the standard username and password authentication flow" (`_index.md:49-52`).
3. **JIT creation.** The account is created at the first LDAP sign-in with username (`attributes.username`, defaults to the `uid` attribute), email (`['mail','email','userPrincipalName']`) and name (`cn`, or first and last name) (`_index.md:486-505`), plus a random password (`password_automatically_set: true`, `GL:lib/gitlab/auth/o_auth/user.rb:242-261`). The email is mandatory: "You must have an email address to use LDAP" (`_index.md:97-98`). `block_auto_created_users` holds new users for admin approval (`_index.md:318`). The email is refreshed at login and at user sync; the name is refreshed at sync when `sync_name` is set (`GL:doc/administration/auth/ldap/ldap_synchronization.md:63-74`; `_index.md:1457-1466`). "LDAP synchronization … does not create new GitLab users through LDAP" (`ldap_synchronization.md:20`).
4. **Same-email collision.** GitLab links automatically by primary email: "The LDAP email address is the primary email address of an existing GitLab user" (`_index.md:37-41`; `o_auth/user.rb:163-167`). There is no setting to turn it off. GitLab's own docs warn against it under "Security risks": use LDAP only if users cannot "Change their `mail`, `email`, or `userPrincipalName` attributes … These users can potentially take over any account on your GitLab server" and cannot "Share email addresses. LDAP users with the same email address can share the same GitLab account." (`_index.md:84-91`).
5. **Removal or disable.** The user is put in a reversible `ldap_blocked` state and is never deleted. GitLab checks "When signing in using any authentication provider", "Once per hour for active web sessions or Git requests using tokens or SSH keys", on Git over HTTP, and "Once per day during User Sync" (`_index.md:56-82`). The hourly check is `sync_time`, default 3600 s (`GL:config/initializers/1_settings.rb:23`; `GL:config/gitlab.yml.example:965-975`; `GL:app/models/user.rb:1990-2003`; `GL:lib/gitlab/user_access.rb:37-38`). Daily user sync runs at 01:30 (Premium, `ldap_synchronization.md:1009-1017`). A user who is no longer active is "Signed out", "Placed in an `ldap_blocked` status", and is "Unable to sign in … until they are reactivated in LDAP" (`_index.md:76-82`). They are unblocked automatically when available again (`GL:lib/gitlab/auth/ldap/access.rb:43-65`). AD disabled accounts (`userAccountControl` bit 2) are blocked with `active_directory: true`. Risk: "All users are blocked if the LDAP server is unavailable when an LDAP user synchronization is run", and the next sync does not unblock them (`ldap_synchronization.md:196-200`).
6. **Role mapping.** `admin_group` and `audit_group` (Premium) give the admin or auditor role. "If an LDAP user has an `admin` role, but is not a member of the `admin_group` group, GitLab revokes their `admin` role when syncing" (`ldap_synchronization.md:360-372`). Otherwise roles are local.
7. **Group sync.** Group links (by CN or filter) run hourly (Premium), and the first sign-in triggers a sync. Access levels can be downgraded. AD nested groups resolve recursively with `active_directory: true`, inside `group_base` only. Local memberships coexist unless "Lock memberships to LDAP synchronization" is on (`ldap_synchronization.md:206-215,663-685,921-976`).
8. **Configuration.** A file only (`gitlab.rb` / `gitlab.yml`), with no UI. Settings: several servers, `encryption: start_tls | simple_tls | plain`, `verify_certificates`, `tls_options` (CA file), `bind_dn`/`password` (encrypted credentials supported), `base`, `user_filter`, `uid` and `attributes` (`_index.md:299-330`).

## 5. Mattermost (Go; AD/LDAP is an Enterprise feature, and its code is closed)

The LDAP implementation is not public: only the interface is in `MM:server/einterfaces/ldap.go:11`. The app-layer calls and the config struct are public.

1. **Identity key.** The configurable **ID Attribute** (`IdAttribute`, empty by default). The docs say: "The attribute should have a unique value that does not change, such as `objectGUID` or `entryUUID`" (`MMD:source/administration-guide/configure/authentication-configuration-settings.rst:808-816`). They also say: "If a user's ID Attribute changes, a new Mattermost account is created that is not associated with the previous account", with `mmctl ldap idmigrate` as the fix. The value is stored on the users row as `AuthService = "ldap"`, `AuthData = <id value>` (`MM:server/public/model/user.go:97-101`; lookup `GetUserByAuth(ldapUser.AuthData, UserAuthServiceLdap)`, `MM:server/channels/app/login.go:124-128`). A separate Login ID Attribute is the field people sign in with (`MM:server/public/model/config.go:2888-2891`).
2. **Login flow.** A mandatory bind account searches: "This is the username for the account Mattermost utilizes to perform an AD/LDAP search … Anonymous bind is not currently supported." (`MMD:…/authentication-configuration-settings.rst:538-556`). There is one form. `GetUserForLogin` looks in the local DB by username or email first, when those sign-in methods are on, and only then asks LDAP by login id (`login.go:96-133`). A row with `AuthService "ldap"` is checked against LDAP; any other row is checked against its local password (`MM:server/channels/app/authentication.go:452-491`). So a local account whose username or email equals the typed identifier wins. To make LDAP the only option, the docs say to turn off email and username sign-in (`MMD:source/administration-guide/onboard/ad-ldap.rst:88-91`).
3. **JIT creation.** The account is created at the first LDAP login inside the closed `DoLogin` ("DoLogin will have created the user", `authentication.go:236-247`). Fields: first and last name, email, username, nickname, position and picture. The email is required: "The AD/LDAP synchronization depends on email" (`ad-ldap.rst:109`). LDAP is authoritative: "the following user attribute changes can't be made through the API: first name, last name, position, nickname, email, profile picture, or username" (`ad-ldap.rst:111`). Attributes are refreshed at login and at each sync.
4. **Same-email collision.** Mattermost does not link automatically. The troubleshooting docs show account creation refusing a duplicate email ("they get an error message `An account with that email already exists` … this means the ID Attribute for their account has changed", `ad-ldap.rst:296`). An existing local account moves to LDAP when its owner does it, proving both credentials: "Security > Sign-in Method > Switch to AD/LDAP" (`ad-ldap.rst:84-86`).
5. **Removal or disable.** `EnableSync` with `SyncIntervalMinutes` default **60** (`config.go:2894`). The docs say: "Disabled AD/LDAP accounts become deactivated users in Mattermost, and any active sessions are revoked." (`authentication-configuration-settings.rst:1053-1067`). A user removed from LDAP, or left out by the user filter, "will be deactivated in Mattermost on the next synchronization", and "all the user's current sessions are revoked" (`ad-ldap.rst:254-268`). AD-disabled accounts are excluded through the user filter `(!(UserAccountControl:1.2.840.113556.1.4.803:=2))` (`ad-ldap.rst:258-260`). Manual deactivation does not stick for LDAP users: "When you manually deactivate a user, they can reactivate themselves by logging back in." (`ad-ldap.rst:256`). The admin console also has "AD/LDAP Synchronize Now".
6. **Role mapping.** The Admin Filter makes matching users system admins at their next login. "If this filter is removed/changed, system admins that were promoted via this filter will be demoted to members" (`ad-ldap.rst:176-195`). There is also a Guest Filter. Otherwise roles are local.
7. **Group sync.** LDAP groups are linked to Mattermost groups by `GroupIdAttribute` ("such as `entryUUID` or `objectGUID`"). Nested groups are supported, and team and channel membership can be synced from groups: "Users removed from an AD/LDAP group are removed from the linked Mattermost group" (`MMD:source/administration-guide/onboard/ad-ldap-groups-synchronization.rst:10-63`).
8. **Configuration.** System Console wizard, `config.json` `LdapSettings`, or `MM_LDAPSETTINGS_*` environment variables (`config.go:2732-2779`). `ConnectionSecurity` is `""`, `TLS` or `STARTTLS`. Also SkipCertificateVerification, a client certificate and key, BaseDN, BindUsername/Password, User/Group/Guest/Admin filters, attribute names, QueryTimeout, MaxPageSize and MaximumLoginAttempts.

## 6. Grafana (Go)

1. **Identity key.** The **DN**: `AuthModule: login.LDAPAuthModule, AuthId: user.DN` (`GF:pkg/services/ldap/ldap.go:484-487`). It is stored in the `user_auth` table (auth module plus auth id), separate from `user`. Grafana looks up by auth info first, then by **email**, then by **login** (`GF:pkg/services/authn/authnimpl/sync/user_sync.go:740-810`). This is not configurable.
2. **Login flow.** "Admin bind" (search with `bind_dn`/`bind_password`) and then a bind as the found DN. A "single bind" alternative uses a `bind_dn` that contains `%s` (`ldap.go:196-266`; `GF:docs/sources/setup-grafana/configure-access/configure-authentication/ldap/index.md:151-171`). `search_filter` defaults to `(cn=%s)`; the docs suggest `(|(sAMAccountName=%s)(userPrincipalName=%s))` to accept a username or email (`ldap/index.md:118-120`). There is one form. The password clients run in the order LDAP, then the local Grafana DB (`GF:pkg/services/authn/authnimpl/registration.go:64-74`), and "we always try next client on any error" (`GF:pkg/services/authn/clients/password.go:61-74`). A local Grafana password therefore still works when the LDAP attempt fails.
3. **JIT creation.** `allow_sign_up = true` by default: "users to be created automatically upon successful LDAP authentication" (`ldap/index.md:40-52`; `GF:conf/defaults.ini:1156`). Fields: name (`name` + `surname` attributes), login (`username` attribute), email, groups (`memberOf`) and org roles (`ldap.go:477-497`). They are synced at every login (`SyncUser: true`, `GF:pkg/services/authn/clients/ldap.go:138-153`).
4. **Same-email collision.** Grafana links automatically: `lookupByOneOf` email, then login, after which the LDAP auth connection is added to the local user (`user_sync.go:768-810`). The contrast inside Grafana: for OAuth, the email lookup is off by default (`oauth_allow_insecure_email_lookup = false`, "Use email lookup in addition to the unique ID provided by the IdP", `defaults.ini:820-821`).
5. **Removal or disable.** In the open-source edition, only at login: when LDAP no longer finds the user, Grafana disables a local user that has an LDAP auth link ("disableUser will disable users if they logged in via LDAP previously", `clients/ldap.go:92-126`). A successful LDAP login re-enables the user (`EnableUser: true`, `user_sync.go:438-457`). Users who match no group mapping, when mappings are configured, are disabled (`ldap.go:525-529`). In Enterprise, "active LDAP synchronization" uses `sync_cron = "0 1 * * *"` (daily at 01:00) and `active_sync_enabled = true` (`defaults.ini:1159-1162`). "Removed users are automatically logged out and their account disabled … Disabled users keep their custom permissions … if you add them back in your LDAP database, they have access to the application with the same custom permissions as before." "Only users that have logged into Grafana at least once are synchronized." (`grafana-enhanced-ldap.md.txt`, from `GF:docs/sources/setup-grafana/configure-access/configure-authentication/enhanced-ldap/index.md`).
6. **Role mapping.** `[[servers.group_mappings]]` maps `group_dn` to `org_role` and `grafana_admin`: "These will be synced every time the user logs in, with LDAP being the authoritative source" (`ldap/index.md:186-190`). `skip_org_role_sync = true` hands roles back to the local admin (`ldap/index.md:55-73`).
7. **Group sync.** Team sync (Enterprise) maps LDAP groups to teams and keeps manual members: "allows you to manually add a user as member of a team, and it will not be removed when the user signs in" (enhanced-ldap docs). Nested groups work through `group_search_filter` with `LDAP_MATCHING_RULE_IN_CHAIN` (`ldap/index.md:248-271`).
8. **Configuration.** `grafana.ini` `[auth.ldap]` plus `ldap.toml`: `host`, `port`, `use_ssl`, `start_tls`, `ssl_skip_verify`, `root_ca_cert`, client cert and key, `bind_dn`, `bind_password` (environment interpolation recommended), `search_filter`, `search_base_dns`, `group_search_*`, `attributes`, `group_mappings` (`ldap/index.md:76-135`). There is also a UI at Administration > Authentication > LDAP (`ldap/index.md:139-141`).

## 7. Keycloak user federation (Java)

1. **Identity key.** A configurable "UUID LDAP attribute". When it is not set, the default follows the vendor: `entryUUID` (other or OpenLDAP), `objectGUID` (AD), `nsuniqueid` (RHDS), `uniqueidentifier` (Tivoli), `guid` (eDirectory) (`KC:server-spi-private/src/main/java/org/keycloak/models/LDAPConstants.java:152-167`; `KC:federation/ldap/src/main/java/org/keycloak/storage/ldap/LDAPConfig.java:171-180`). It is stored on the imported user as the attribute `LDAP_ID`, with `LDAP_ENTRY_DN`, and `federationLink` = the provider's component id (`KC:federation/ldap/src/main/java/org/keycloak/storage/ldap/LDAPStorageProvider.java:686-694`). On access, the stored `LDAP_ID` is compared with the directory (`:644-670`). The failover docs assume this key: "Each LDAP entry must have the same unique identifier (such as `entryUUID` or `objectGUID`) across all servers" (`KC:docs/documentation/server_admin/topics/user-federation/ldap.adoc:119`).
2. **Login flow.** One realm login form (username, or email when the realm allows it). Keycloak looks in the local DB first ("first try the local storage"), then in the enabled storage providers (`KC:model/storage-private/src/main/java/org/keycloak/storage/UserStorageManager.java:1305-1324`). The password is always checked by binding to LDAP: "Keycloak never imports passwords. Password validation always occurs on the LDAP server." (`ldap.adoc:26`; `LDAPStorageProvider.java:822-840`). Searches use the configured bind DN.
3. **JIT creation.** "The first time a user logs in or is returned as part of a user query … the LDAP provider imports the LDAP user into the Keycloak database" (`ldap.adoc:136`). Mappers copy username, email, first and last name, and any extra attributes. Email is optional. Refresh depends on Edit mode (READ_ONLY / WRITABLE / UNSYNCED, `ldap.adoc:50-62`), on the mappers' "Always Read Value From LDAP", and on periodic sync.
4. **Same-email collision.** Keycloak refuses. A same-username local account that is not linked raises `ModelDuplicateException("User with username '…' already exists in Keycloak. It conflicts with LDAP user with email '…'")` (`LDAPStorageProvider.java:790-801`). Sync skips such users: "User with ID '%s' is not updated during sync as he already exists in Keycloak database but is not linked to federation provider" (`KC:federation/ldap/src/main/java/org/keycloak/storage/ldap/LDAPStorageProviderFactory.java:796-798`). Because the local DB is looked up first, a same-username local account is used at login.
5. **Removal or disable.** Detected when the user is looked up (login, admin search) and not cached. **Remove invalid users during searches** is on by default (`isRemoveInvalidUsersEnabled` → `true`, `KC:model/storage/src/main/java/org/keycloak/storage/UserStorageProviderModel.java:128-136`). With it on, the imported user is **deleted**. With it off, the user is "kept in the local database, as read-only and disabled, even if that user is no longer available from the user storage" (`ldap.adoc:82-83`; `UserStorageManager.java:180-198`). Periodic Full sync and Changed users sync are off by default (`fullSyncPeriod` = -1, `UserStorageProviderModel.java:69-76`). They import and update users; the sync code reviewed has no removal step. The MSAD account mapper treats `userAccountControl` 514 as disabled (`ldap.adoc:192`).
6. **Role mapping.** A Role mapper maps LDAP groups to realm or client roles, and a Hardcoded role mapper gives every LDAP user a role (`ldap.adoc:182-187`). Modes are `LDAP_ONLY`, `IMPORT` ("retrieved from LDAP … just at the time when he is imported") and `READ_ONLY` (merged with DB grants) (`KC:federation/ldap/src/main/java/org/keycloak/storage/ldap/mappers/membership/LDAPGroupMapperMode.java`).
7. **Group sync.** A Group mapper uses the same modes. Options: "Preserve group inheritance", retrieval strategies including `LOAD_GROUPS_BY_MEMBER_ATTRIBUTE_RECURSIVELY` (nested groups) and `GET_GROUPS_FROM_USER_MEMBEROF_ATTRIBUTE`, a "Groups path" that places LDAP groups under a subtree beside local groups, and "Drop non-existing groups during sync" (`KC:federation/ldap/src/main/java/org/keycloak/storage/ldap/mappers/membership/group/GroupMapperConfig.java:40-71`).
8. **Configuration.** Admin console or admin REST, stored per realm component: vendor, connection URL (LDAPS, or a StartTLS switch), truststore, bind type/DN/credential, users DN, username, RDN and UUID attributes, object classes, custom filter, scope, edit mode, Import users, Sync registrations, sync periods, Kerberos, connection pool (`ldap.adoc:68-131,234-266`).

## 8. Nextcloud `user_ldap` (PHP)

1. **Identity key.** The UUID is detected automatically from `entryuuid`, `nsuniqueid`, `objectguid`, `guid` and `ipauniqueid` (`NC:apps/user_ldap/lib/Access.php:38`), with an "Override UUID detection" setting. The mapping tables `ldap_user_mapping` and `ldap_group_mapping` tie the DN, the UUID and a permanent internal name together: "If the DN changes in LDAP it will be detected, and there will be no conflicts." (`NCD:admin_manual/configuration_user/user_auth_ldap.rst:845-856`). By default the internal username _is_ the UUID (`Access.php:556-565`; docs `:569-575`).
2. **Login flow.** The Login Attributes tab matches the typed name against the LDAP username (`uid`/`samaccountname`, auto-detected), the email (`mailPrimaryAddress`, `mail`), other attributes, or a raw filter (`user_auth_ldap.rst:145-175`). An agent DN searches, then Nextcloud binds as the user (`NC:apps/user_ldap/lib/User_LDAP.php:142-181`, `areCredentialsValid`). There is one login form for all user backends.
3. **JIT creation.** Creation is not tied to login: LDAP users become Nextcloud users as soon as they are first seen (listing, sharing autocomplete, login). Attributes (email, quota, avatar and others) update "on every login, on first detection of a new user, and periodically via a background job" that targets about one pass a day, with an interval kept between 30 minutes and 12 hours (`user_auth_ldap.rst:653-662`).
4. **Same-email collision.** Nextcloud never merges. If the internal name is taken by any backend, local users included, it appends a suffix: "On collisions a random number (between 1000 and 9999) will be attached … if "alice" exists, the next username may be "alice_1337"." (`user_auth_ldap.rst:576-580`; `Access.php:600-627,786-799`). With the default UUID-based names, collisions do not arise. The result is always a separate account.
5. **Removal or disable.** The `CleanUp` background job checks mapped users in chunks of 50 and marks missing ones as deleted ("remnants") (`NC:apps/user_ldap/lib/Jobs/CleanUp.php:155-170`). The interval comes from `ldapUserCleanupInterval`. The code default is **60** minutes (`CleanUp.php:33,52-55`), while the docs say "The default is 51 minutes" (`NCD:admin_manual/configuration_user/user_auth_ldap_cleanup.rst:23-24`). "Disable users missing from LDAP" (`markRemnantsAsDisabled`, default false) makes remnants "behave as if disabled" (`User_LDAP.php:669-675`; `user_auth_ldap.rst:351-354`). Deletion is manual: `occ ldap:show-remnants`, then `occ user:delete`. The flag is cleared automatically when the user is found on LDAP again (`User_LDAP.php:315-317`; `Access.php:721-730`).
6. **Role mapping.** One LDAP group per configuration can be the admin group (`occ ldap:promote-group`, `ldapAdminGroup`). It is checked live (`isAdmin` → `inGroup`, `NC:apps/user_ldap/lib/Group_LDAP.php:1420-1432`; `user_auth_ldap.rst:666-700`). Otherwise roles are local.
7. **Group sync.** LDAP groups appear as a read-only group backend beside local groups. A Nested groups option exists, and a background job refreshes a membership cache (`user_auth_ldap.rst:395-399,810-820,873-877`).
8. **Configuration.** Admin wizard (Server, Users, Login Attributes, Groups, Advanced, Expert), several configurations, and `occ ldap:*` commands. TLS through LDAPS or StartTLS, with certificate handling through the system's LDAP settings (`user_auth_ldap.rst:278-290,783-800`).

## next-auth v4: documented stance on linking accounts by email

- FAQ: "Automatic account linking on sign in is not secure between arbitrary providers - with the exception of allowing users to sign in via an email addresses as a fallback (as they must verify their email address as part of the flow)." It continues: "With automatic account linking on sign in, this can be exploited by bad actors to hijack accounts by creating an OAuth account associated with the email address of another user." And: "It can be technically possible to do automatic account linking securely if you trust all the providers involved … Examples … include with an OAuth provider you control (e.g. that only authorizes users internal to your organization)" (`NA4:docs/docs/faq.md:223,227`; `NAD:docs/faq.md:204-220`).
- Error page: "**OAuthAccountNotLinked**: If the email on the account is already linked, but not with this OAuth account" (`NA4:docs/docs/configuration/pages.md:52`).
- `allowDangerousEmailAccountLinking`: "Normally, when you sign in with an OAuth provider and another account with the same email address already exists, the accounts are not linked automatically. Automatic account linking on sign in is not secure between arbitrary providers and is disabled by default … it may be desirable to allow automatic account linking if you trust that the provider involved has securely verified the email address" (`NA4:docs/docs/configuration/providers/oauth.md:286-290`). The code throws `AccountNotLinkedError("Another account already exists with the same e-mail address")` unless the flag is set (`NA4:packages/next-auth/src/core/lib/callback-handler.ts:182-200`).
- Relevance to the hub: Credentials sign-ins never reach that adapter logic ("users authenticated in this manner are not persisted in the database, and consequently that the Credentials provider can only be used if JSON Web Tokens are enabled", `NA4:docs/docs/providers/credentials.md:12`). An LDAP sign-in through Credentials therefore puts the linking rule in the hub's own DAL. next-auth's documented default (do not link by email, and show a "not linked" error) is the documented precedent for the owner's rule.

## Patterns most projects share

1. **Every account records its source.** All but Open WebUI record which backend owns an account: `provider` (LibreChat), `services.ldap` + `ldap:true` (Rocket.Chat), an `identities` row (GitLab), `AuthService` (Mattermost), a `user_auth` row (Grafana), `federationLink` (Keycloak), the mapping table (Nextcloud). This matches the owner's "every account tagged local or LDAP".
2. **Search-then-bind with a service account is the norm.** All eight bind (or, where allowed, search anonymously), find the entry with a configurable filter or attribute, then bind as that DN. Only Grafana also offers a direct "single bind". Mattermost requires the bind account. Open WebUI and ldapauth-fork allow anonymous binds.
3. **The directory checks the password, and the password is not stored.** Keycloak states it outright ("never imports passwords"). LibreChat, Mattermost and Nextcloud store none. GitLab and Open WebUI store a random password nobody knows. Rocket.Chat stores the real LDAP password only when Login Fallback is turned on.
4. **Accounts are created at the first login, with the directory as source of truth for profile fields.** Name and email are refreshed at login and/or sync, and several projects make LDAP fields read-only (Mattermost, Keycloak READ_ONLY). Nextcloud creates them at first detection instead.
5. **Removal deactivates the account and does not delete it.** GitLab (`ldap_blocked`), Mattermost (deactivated), Rocket.Chat (inactive, premium), Grafana (disabled), Nextcloud (remnant, optionally disabled, deleted only by hand). Keycloak's default deletes the _imported copy_; its option keeps it read-only and disabled.
6. **Removals are found by a scheduled job plus checks at login.** Mattermost runs every 60 min, Nextcloud every 51 or 60 min (docs vs code), GitLab hourly per user plus daily, Grafana Enterprise and Rocket.Chat daily by default. Several also revoke sessions on deactivation (GitLab "signed out", Mattermost "sessions are revoked", Rocket.Chat unsets login tokens, Grafana "automatically logged out").
7. **Role mapping from groups is opt-in.** Without it, roles stay local. When it is on, it is re-applied at every login or sync and wins over local edits: Grafana ("LDAP being the authoritative source"), GitLab `admin_group` ("revokes"), the Mattermost Admin Filter ("demoted"), Rocket.Chat with Auto Remove.
8. **Group sync keeps local groups beside directory groups** in GitLab (unless locked), Grafana team sync, Keycloak (groups path, READ_ONLY mode), Nextcloud and Mattermost. Open WebUI is the exception.

## Where they disagree

- **Identity key.** A stable UUID (Keycloak by vendor default, Mattermost's recommendation, Nextcloud auto-detect, Rocket.Chat default list) against the DN (GitLab, Grafana), login names (LibreChat: uid/sAMAccountName/mail) and the email (Open WebUI). The DN-keyed projects then fall back to **email** to re-find users whose DN changed (GitLab, Grafana). GitLab documents the resulting takeover risk.
- **Same email or username as a local account.** _Refuse_: LibreChat, Keycloak, Mattermost, Rocket.Chat (default). _Separate account_: Nextcloud. _Auto-link_: GitLab, Grafana, Open WebUI. The two auto-linkers that also do OAuth (Grafana, Open WebUI) switch email-based matching **off by default for OAuth** and call it insecure, yet keep it for LDAP. That treats the directory as a trusted, verified source.
- **Login form and precedence.** LDAP-only form (LibreChat). A separate LDAP mode or tab (Open WebUI, GitLab). One form with LDAP tried first (Rocket.Chat, Grafana). One form with the local account first (Mattermost, Keycloak).
- **What removal does.** Block or disable (GitLab, Mattermost, Grafana, Rocket.Chat). Delete the local copy (Keycloak default). Flag with optional disable and manual delete (Nextcloud). Nothing (LibreChat, Open WebUI).
- **Re-activation when the entry comes back.** Automatic: GitLab (next check), Grafana (next login), Nextcloud (flag cleared). Opt-in: Rocket.Chat (only with active-state `enable`/`both`). Mattermost reverses even a manual deactivation at the next LDAP login.
- **Missing email.** Refused: Open WebUI, GitLab, Mattermost, and Rocket.Chat without a default domain. Synthesized: LibreChat `@ldap.local`, Rocket.Chat `username@Default_Domain`. Optional: Keycloak.
- **Group sync and local memberships.** Open WebUI replaces all memberships at each login. GitLab can lock them. Grafana keeps manual team members. Keycloak and Nextcloud keep LDAP groups apart from local ones.

## Owner's model against common practice

| Owner's rule | Matches | Departs |

Open points the owner's model does not settle yet. Each one has precedents both ways:

- **Re-activation.** Should a deactivated LDAP account be re-activated automatically when the entry comes back? GitLab, Grafana and Nextcloud do; Rocket.Chat's default does not.
- **Admin deactivation.** Does an admin's manual deactivation survive an LDAP login? Mattermost says no.
- **Sessions.** Are sessions revoked when the account is deactivated? GitLab, Mattermost, Rocket.Chat and Grafana revoke them, and GitLab also re-checks live sessions hourly.
- **Form precedence.** Does the hub's one form try local or LDAP first?
- **Directory outages.** How is "not found" told apart from "directory unreachable"? GitLab blocks everyone when its sync runs during an outage; Nextcloud's docs require every configured LDAP server to be up before cleanup.
